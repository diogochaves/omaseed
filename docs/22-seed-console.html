The seed console

omaseed runs all day in the tray, so it can do the one thing a web UI and qBittorrent's own counters can't: remember. This board proposes a second face for the main window, a console about what you give back to the swarm, plus eight small touches in the library that make seeding visible where you already look. Everything stays in the shell's idiom: monospace, hairlines, tracked captions, Theme roles, no cards, no shadows, no rounded corners.

Every number in the mocks is example data, generated in this page from a made-up library of public-domain films, Linux images, open datasets and Musopen audio. Switch the theme in the bar below: the mocks only use roles, so they follow it.

1 · where we are

The library today, and what already exists to build on

Seeding is already in the data, just not on screen

  • The bar widget (docs/19, docs/20) already gets I1–I7 from the app: session share, a 60-minute upload sparkline, the "keeping alive" tallies, top seeders, an 8-day strip and ratio milestones.
  • StatusDigest::UploadSampler samples upload every second; UploadDays keeps per-day totals, but only the last eight days.
  • GlobalState already parses alltime_ul, alltime_dl and global_ratio; nothing in the window draws them.
  • The table has num_complete / num_incomplete, ratio, uploaded, seeding_time, last_activity per row. The S / P column shows connected peers, so "you are the only seed" is invisible today.
The console turns those eight days into a ledger that keeps everything, and gives the big window the view the widget can only summarise. The widget keeps reading what it reads now; its sections link into the console.

What nobody does well

  • Remembering. Front ends keep 15 points to 24 hours; only server-side tools keep more. A tray-resident client is the natural place for history.
  • Rare seeds up front. Being the last seed only shows up as a hidden rank (BiglyBT) or a tracker's multiplier.
  • Earning against holding. No tool ranks the torrents that upload against the ones that take disk and upload nothing.
  • Health tied to seeding. An unregistered torrent or a firewalled port earns nothing, silently; qui shows counts, nobody shows the cost.

What that gives the console

  • The ledger (§3), so the tide, the year and "30 days" per tracker exist at all.
  • Keeping alive as its own block, and rarity in the table (T3) and on delete (T6).
  • Earning and holding: 30-day yield (ruTorrent's ratio per month) beside the dead weight, by size.
  • One attention line over the console when something stops you earning: a tracker not working, the port closed.
  • Seeded × in the trackers table, as qui does, and buffer in the totals, as trackers do.

API facts that shaped the mocks: global_ratio is a string ("-" when a total is 0); availability is −1 while seeding, so rarity has to come from num_complete / num_incomplete (the tracker's scrape, −1 when there is none); qBittorrent has no history endpoint; clientdata/load|store (5.2+) is a 1 MiB JSON store on the server every client shares; per-peer contribution only arrives with 5.3 (API 2.16).

3 · the idea underneath

The ledger: omaseed is always on, so it remembers

qBittorrent only keeps running totals: what each torrent has uploaded since it was added, and what the server has moved since it was installed. It keeps no history. qui and VueTorrent can only draw what happened while their tab was open. omaseed is resident in the tray and already polls every second, so it can turn those totals into a history and keep it.

qBittorrent

running totals, no historyalltime_ul alltime_dlper torrent uploaded downloadedup_info_speed each second

→ the sampler

each poll: new total − last totala negative step (a qBittorrent reinstall, a torrent re-added) starts a new baseline instead of counting as a loss

→ the ledger

one SQLite file per serverseconds: last hour, in memoryminutes: 48 hhours: 90 daysdays: forever, total and per torrent

→ who reads it

one sourcethe consolethe bar widget (I2, I5 move onto it)milestone toasts and the weekly recap
While omaseed is closed, qBittorrent keeps seeding. On the next start the totals have grown: the difference is exact, only its spread over the hours is unknown. The ledger spreads it evenly and marks the span, and the tide draws it hatched with a label ("omaseed was closed · 2.1 GB over 9 h"). Nothing is invented and nothing is lost.
Day one has no history, but qBittorrent's all-time totals are already there. The console opens with those, and the year says plainly where the ledger begins ("before 3 Oct: 4.21 TB given"). Use the day one switch above to see it.
Another machine. qBittorrent 5.2 added clientdata, a 1 MiB JSON store on the server that every client shares. The daily totals (about 15 KB a year) could be mirrored there, so a laptop pointed at the same server sees the same year. Optional, D10.
Cost. One row per server per minute (2,880 kept), one per hour (2,160), one per day, and per torrent one row per day it actually uploaded. A 1,000-torrent library that seeds every day adds about 1 MB a year. QtSql's SQLite driver ships with qt6-base: no new dependency.

6 · outside the console

Eight small touches in the library

The console is where you go to look. These are where seeding shows up while you are doing something else. Each one is small, uses a shape the app already has, and stands on its own: pick any of them in the decision sheet.

7 · building it

How it would be built, in order

core (QtTest first, as always)

  • SeedLedger: the sampler and the SQLite file per server under ~/.local/share/omaseed/. Baselines, negative steps, gaps spread evenly, the four resolutions and their pruning. Takes "now" as an argument so tests walk days.
  • UploadSampler and UploadDays fold into it; the status file reads the ledger, so the widget's week strip can show more than eight days without changing its schema.
  • ConsoleModel: totals, buckets, ladder points and tracker rows for a scope (the rail's current filter, or a selection), recomputed on the table's updated, throttled to once a second.

kit and views

  • Kit gets Sparkline, AreaChart (two series about a baseline, hatched spans, a crosshair), DayGrid and StackStrip, all on QtQuick.Shapes, with tst_*.qml each. A chart ramp of the seeding colour at 22 / 45 / 70 / 100 % becomes a Theme function next to fill().
  • Views/Console.qml in the body's place; the hero gets the two view tabs; Keymap gets a console area (`, [ ], j k, enter, esc).
  • Each library touch is its own commit and issue, after the console.

checks

  • The swarm (swarm.sh) gives real uploads on the playground: a new seed-walk.sh seeds, closes omaseed for a while, reopens, and checks the gap is counted and hatched.
  • Shots of the console in an app box for every block, in a dark and a light theme, at base 12 and 14.
  • Idle CPU with the console open and hidden, against today's number in REVIEW-v0.1.0.md §3.
This is a v2-sized feature and a departure from the frozen spec: once ruled, it gets its REVIEW-v0.1.0.md line and one GitHub issue per piece (ledger, console, each touch). Nothing here blocks #4 or #5. My suggestion (D9): the ledger now, core only and invisible, so history starts with your real library; the console and the touches after v0.1.0 ships.
