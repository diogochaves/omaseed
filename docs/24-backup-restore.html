Backup and restore

Board 22 gave omaseed something worth keeping: a seed history that only this app records. The charter (§10) already planned "backup/restore of qBittorrent config, export/import per server". This board covers both. omaseed backs itself up (settings, servers, history). It also exports and imports a qBittorrent: its settings, and separately its torrents, so you can set up a new server like the old one or move a library to a new machine. Everything goes through the WebUI API, so it works the same for a local qBittorrent, one in a container and a remote seedbox.

Every name, path, count and size in the mocks is example data. Switch the theme in the bar below: the mocks use Theme roles only.

Already settled by your answers (2026-10-03): omaseed's backup holds settings + servers + history, no passwords. qBittorrent export covers settings and torrents as two separate choices. Importing settings shows a preview and leaves machine-specific values out unless ticked. Board first, then code. The open calls are D1–D9 at the bottom.

qBittorrent can't export any of this itself through its WebUI. Its desktop GUI can't either, apart from saving single .torrent files. qui (autobrr) does instance backups server-side. omaseed can do it from the desktop because the API exposes every piece: app/preferences (223 keys on 5.2.3), torrents/categories, torrents/tags, rss/items and rss/rules, and torrents/export, which returns a torrent's .torrent file. It answers 409 Missing metadata for a magnet that never got its metadata; those are kept as magnet links.

7 · edge cases

What could go wrong, and what omaseed does

  • Backup from another machine. Servers are matched by address. If the address changed (a new IP for the box), the restore sheet asks "is 192.168.1.20:8080 the same as home?"
  • History on both sides. D4. The default keeps the longer history and saves the other aside, so nothing is thrown away.
  • Older or newer qBittorrent. Keys the target doesn't have are skipped and counted. Keys the file doesn't have stay as they are. Categories' share limits need 5.x; on 4.x they are skipped with a note.
  • A torrent already on the target (same hash): skipped (D8).
  • Cross-seeded torrents (two hashes, same files): both come back, pointed at the same folder, so they keep sharing one copy on disk.
  • A torrent in a moving state or checking at export: its target save path is the one exported.
  • Huge libraries. Export reads .torrent files 20 at a time with a progress line. A 3,000-torrent export is about 150 MB.
  • An import fails halfway (server gone, disk full): what was added stays, the sheet says how far it got, and running it again skips what is already there.
  • The file is from a different app, or damaged: refused before anything changes, with the reason.
  • Automatic copies on a full disk: skipped with a notice. The oldest copies are removed only after a new one is written.
8 · building it

How it would be built

core

  • TarArchive: write and read plain ustar, no dependency.
  • OmaseedBackup: collects state.json, servers.json and each ledger (the SQLite backup API, safe while the app runs). Restores the chosen parts after the safety copy.
  • QbtExport / QbtImport: preferences minus secrets; categories, tags, RSS; torrents with torrents/export + info + files. The import diffs, sorts machine-specific keys, then applies in order: categories, tags, preferences, RSS, torrents.
  • A QtTest for each, with fixtures.

views

  • Two Backup panes in SettingsModal, built from the existing rows and chips.
  • Three Kit Sheets: restore, import settings, import torrents.
  • The file picker is the portal one the add sheet already uses.

checks

  • Live tests export from the :8081 playground.
  • A new backup-walk.sh exports from one box qBittorrent (app-box.sh up --qbt), imports into a second, empty one, and compares everything on both servers and on disk: settings, categories, tags, RSS, every torrent's path, category, tags, limits and state.
  • The same walk restores omaseed into a fresh box and checks the console shows the same year.
This adds two Settings panes and three sheets that the frozen spec doesn't have. Once ruled: a REVIEW-v0.1.0.md line and an issue per part.
