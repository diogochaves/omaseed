The add sheet knows the library

Three changes to adding a torrent, all built on what omaseed already knows when a source is loaded: its infohash, its trackers, its file list and its size. A duplicate can merge its trackers into the torrent already there, unless either side is private (#26). Files already on disk under another torrent are found, and the sheet offers to save there, so the new torrent checks and seeds with nothing to download (#27). Save to says how much room is left where the files will go (#29).

Every name, tracker, path and size in the mocks is example data. Switch the theme in the bar below: the mocks use Theme roles only. The screenshots in §1 are real.

Settled when these issues were filed: merging stays out for private torrents; the files match is found offline, with no indexer client, inside board 23's line (its D8); magnets get no files match because they have no file list until their metadata arrives. Board first, then code. The open calls are D1–D10 at the bottom.

Today: the sheet knows the hash, and says so late

What the sheet already has when a source loads:
  • Infohash, v1 and v2. The Downloads list already marks rows "in library", but the form still opens in full and the duplicate only shows on add.
  • Trackers from announce / announce-list (TorrentFile), or a magnet's tr=.
  • Private flag, on the file and on every library row (private in maindata, 5.0+).
  • File list and sizes (the files tree), so the "needs" figure and a files match cost nothing extra.
  • Each library torrent's name, total_size, save_path, content_path and tracker, from maindata.
2 · #26

A duplicate can bring its trackers along

The same infohash from another source is common with public torrents: a magnet from one site, a .torrent from another, each listing different trackers. qBittorrent's desktop app offers to merge them. omaseed stops the add before the server sees it, so it does the merge itself with torrents/addTrackers, which works whatever the server's own "merge trackers" setting says. A private torrent is never merged. qBittorrent refuses that too: adding another site's tracker to a private torrent leaks it outside its tracker.

+2 trackers added to Public Domain Samplerits Trackers tab is open
← after merge (D3 a): the sheet closes, the table's cursor goes to the torrent and its details open on Trackers, where the new rows are shown "not contacted yet".
When it says so (D1). The sheet already knows the hash when a source loads, because the Downloads list marks rows "in library". With D1 a, a duplicate turns straight into this sheet instead of the full form. You don't fill in a category and tags only to be told no at add. A queued batch (several files dropped) still shows each duplicate in turn.
What merge leaves alone. Only trackers are merged, not the sheet's category, tags or limits. Web seeds (url-list) aren't merged in this first step: they're rare on public torrents, and trackers are what the issue is about.
3 · #27

These files are already on disk: save there

The same release from two trackers has two infohashes: each private tracker stamps its own source in the file. So it isn't a duplicate, and qBittorrent sees two unrelated torrents. Saving the second one where the first one's files already are is cross-seeding. libtorrent finds the files, checks them, reaches 100 % and seeds both swarms from one copy, with nothing downloaded. Saving it anywhere else downloads everything a second time.

tracker A's torrentalready in the library, seeding/media/music/Field Recordings Vol. 3 [FLAC]/16 files · 103 MB
tracker B's torrent, saved theresame 16 paths and sizes, another hash→ checked 100 %, seeds right away, 0 B downloadedone copy on disk, two swarms
tracker B's torrent, saved elsewherethe default folder, say→ 103 MB downloaded againtwo copies; the second seeds only once it's done

qui and the cross-seed tool find these from indexers. omaseed won't grow an indexer client (board 23, D8). But when you're the one adding the second torrent, it can compare it with the library at no cost and offer the folder.

Same name, different files. Matching is on paths and sizes, never on the name alone. Two "Discography [FLAC]" uploads of different rips have the same name and different sizes, and step 1 already keeps them apart.
The torrents now share data. Deleting either one with its files takes the other one's files away. That's board 26 (#28): the delete confirm finds torrents that share files whichever way they were added, through omaseed, qui or cross-seed.

Save to says how much room is left

One line under Save to: what the torrent needs (the ticked files only), what's free where it will go, and a small meter. It follows Save to as it changes: the default, a category's folder, a typed path, the picker, "save there". The line turns yellow when the add would leave less than the low-disk threshold (Settings › Notifications, 2 GiB by default, the same number as the "disk almost full" notice). It turns red when the torrent doesn't fit.

any other folder, server on this machineQStorageInfo on the folder, or on its nearest existing parent (a new folder doesn't exist yet), read here every time Save to settles"free on mount point"
any other folder, remote server with a path mapthe same, on the folder the path map turns it into (PathMap::toLocal, as "open folder" does)"free on mount point"
any other folder, remote, no mapnothing the API offers: there's no free-space call for a path, and app/getDirectoryContent lists names only"unknown", with the default folder's figure for scale (D8)
"On this machine" is checked, not assumed. A qBittorrent in Docker on 127.0.0.1 sees /downloads, and this machine has no such folder. Its nearest parent here would be /, which gives the wrong drive. So once per connection, omaseed reads its own figure for the default save path and compares it with free_space_on_disk. If they agree within 1 %, it reads local figures for other folders. If they don't, the server is treated as remote, with or without a path map.
Board 23's N1 (unruled, #25) puts a folder line under the category chips. If both are taken they become one line under Save to, e.g. "saves to ~/Media/films · filed automatically · needs 48.2 GB · 1.2 TB free", so the sheet doesn't grow by two lines.
5 · building it

How it would be built

core

  • TrackerMerge: the new source's URLs minus the torrent's (normalised: scheme, host and port compared lower-case, a trailing /announce kept). QtTest.
  • LibraryMatch: a parsed TorrentFile against candidates' file lists. It returns exact, near (counted) or none, plus the save path and layout that make the root line up. QtTest with fixtures for single-file, folder and no-root torrents.
  • FreeSpaceProbe: Save to → bytes free and mount point, or unknown. Covers the default path, local reads, path maps and the calibration check. QtTest with an injected storage reader.

views

  • DuplicateSheet: the tracker block, the private line, a third button. It opens from the source load (D1 a).
  • AddSheet: the match line under the source, and the free line under Save to. Both are plain rows on existing Kit parts: the banner of Fig. 10, and a ProgressLine for the meter.
  • App: duplicateTrackers(hash, urls), filesMatch(source), freeSpaceFor(path); merge reuses addTrackers.

checks

  • magnet-walk.sh grows two steps. A public fixture added twice with different trackers merges, checked on the server's tracker list. A private one shows M2.
  • A new crossseed-walk.sh on a box qBittorrent (app-box.sh up --qbt). swarm.sh writes a second .torrent of a seeded torrent's files with another source. The walk adds it with "save there" and checks it reaches 100 % with 0 B downloaded and one copy on disk.
  • Free space: unit tests for every row of the table. The walk reads the line for the default folder against the footer's figure.
This changes Fig. 10 and the add sheet of the frozen spec. Once ruled: a REVIEW-v0.1.0.md line, and the work done under #26, #27 and #29, one commit per decision.
