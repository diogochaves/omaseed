Deleting files another torrent is seeding

Two torrents can use one copy of the same files: a cross-seed from another tracker, added through omaseed (board 25), qui or the cross-seed tool. qBittorrent doesn't know they share anything. Delete one with its files, and the other one loses its data, drops to "missing files" and stops seeding. qui checks for this before a delete. omaseed's delete confirm will too: it names the torrents that share the data, keeps the files by default, and offers to delete the others along with them.

Names, trackers and paths in the mocks are example data. The screenshot in §1 is real. Switch the theme in the bar below: the mocks use Theme roles only.

1 · where we are

Today: the confirm guards the swarm, not the disk

The confirm counts the torrents and their size on disk. It remembers the files switch and warns when you're one of the last seeds. Nothing in it looks at what else uses those files. qBittorrent's torrents/delete with deleteFiles=true removes the torrent's files and any folders left empty, whoever else is seeding them.

2 · the proposal

Say who else uses the files, keep them by default

When the files switch is on (opened with D, or switched on in the dialog), the confirm looks for torrents outside the selection that use the same data. When it finds some, it lists them and offers a choice in place of the plain switch. When none are found, the confirm is exactly as today.

Option B for D1 is smaller: no choice rows. When sharers exist, the switch turns itself off with the yellow line under it, the button reads delete, keep files, and a second button delete 2 with files takes the sharers along. There are no rows to move between, but the switch no longer simply shows what you set.
3 · detection

What counts as "the same data"

casehow it's foundcosts
same folder or fileequal content_path: two torrents with the same root folder, or the same single file, under the same save path. This is how every cross-seed tool adds onenothing: maindata is in memory
one inside the otherone content_path under the other's: a season pack and one episode added on its own, a discography and one albumnothing
no root foldera torrent added with "No subfolder" has content_path equal to its save path, so it would look as if it shares with everything in that folder. For these, and only when the save paths are equal, the two file lists (torrents/files) are compared path by pathone GET per such torrent, when the confirm opens
hardlinks, reflinksdifferent paths, so not shared. Deleting one copy leaves the other intact, which is the point of linking (qui and cross-seed's link mode)never flagged
another serverout of reach: omaseed only sees the server it's on. A NAS seen by two qBittorrents is outside this check, and the line doesn't claim otherwise
Paths compared as the server writes them: after trimming a trailing slash, case-sensitive, never mapped to local paths. Two torrents only share data when the same qBittorrent sees the same path.
Sharers in any state count: seeding, stopped, queued, checking. A sharer already in "missing files" is listed too, marked so: deleting the files can't hurt it further, but you may want it gone as well.
4 · the same problem, moving

Set location and category moves break it too

Moving one torrent of a pair (torrents/setLocation, or a category change with automatic management on) moves the files out from under the other one. That leads to the same "missing files" as a delete. The detection above is the same, so D4 asks whether the location sheet and a category change get the same line now or later.

5 · building it

How it would be built

core

  • SharedData: given the selection and the library rows (hash, save path, content path), it returns each selected torrent's sharers outside the selection. Plus the no-root case: which torrents need their file lists fetched. Pure, with a QtTest covering every row of §3.
  • The "on disk" figure counts shared data once (S4).

views

  • DeleteConfirm: the yellow line, the two choice rows and the button text, all only when the switch is on and sharers exist. The order is files question first, then the last-seed line.
  • App.deleteTorrents takes two lists (with files, without), so "keep their files" is one confirm and two calls.
  • With D4 a: the same line in the location sheet, and a notice when a category change would move one of a pair.

checks

  • actions-walk.sh grows a step on a box qBittorrent (--qbt). It adds board 25's second .torrent beside the first, deletes one with D and "keep the files", then checks on the server and on disk that the other is still 100 % and its files are there. It runs again with "delete both" and checks the folder is gone.
  • The "no root folder" case gets its own fixture, so the file-list comparison is exercised live.
