Why a torrent errored

When qBittorrent puts a torrent in error, omaseed shows the word "error" and nothing else, so you have to go to qBittorrent's Web UI log to find out why. qBittorrent's API never gives the reason. Its log does, as one line naming the torrent, and libtorrent stamps that line with the first characters of the torrent's info hash. omaseed can read the log, tie each line to its torrent, and say in plain words what went wrong, with the action that fixes it next to it.

The screenshot in §1 and every log line in §2 are real: the :8081 playground (qBittorrent 5.2.3, libtorrent 2.1.1), broken with swarm.sh break error and break missing. The other names and times in the mocks are example data. Use the theme switch below: the mocks use Theme roles only.

2 · what qBittorrent gives

The reason is only in the log, and the log ties it to the torrent by name

Not in the API

qBittorrent keeps the reason itself. Its desktop app shows Errored: <reason> in the status column, from TorrentImpl::error() (libtorrent's error code, or "couldn't write, now in upload-only mode"). The Web UI API doesn't return it: torrents/info and torrents/properties have state: "error" and no message (checked on 5.2.3: 63 fields, none an error).

In the log, as a warning

GET /api/v2/log/main returns {id, timestamp, type, message}. Type 4 is a warning. qBittorrent writes one line when libtorrent reports a file error, at most once a second per torrent, and again every time the torrent is started or the server restarts.

id 30 · type 4 · 1791928475 File error alert. Torrent: "unwritable-fixture.bin". File: "/…/swarm-readonly/unwritable-fixture.bin". Reason: "ad91d5 file_open (/…/swarm-readonly/unwritable-fixture.bin) error: Permission denied" id 28 · type 4 · after a restart, the files deleted Failed to restore torrent. Files were probably moved or storage isn't accessible. Torrent: "tiny-notes.txt". Reason: "81f2da fast resume rejected. file_stat(/…/swarm/tiny-notes.txt): mismatching file size"

How the line is tied to its torrent

Torrent: "name"qBittorrent's own wrapper, torrent->name(). This is the only way qBittorrent itself names the torrent. There is no hash in its part of the line.no: two torrents can share a name, and a cross-seed always does
File: "path"Only in file errors: the full path libtorrent was using. It falls under exactly one torrent's save path (or download path)nearly always, unless both torrents save to the same folder

operation, errorlibtorrent: file_open, file_write, mkdir, file_fallocate, file_stat…, then the system's message (strerror)what went wrong, used for the plain wording in §5
The log is translated. qBittorrent writes these lines in its own language ("File error alert. Torrent:" is tr()). So omaseed never matches the English words. It looks for "<name>" in quotes, a path under a save path, and the 6-hex prefix, which are the same in every language.
The log is in memory. It holds 20 000 lines and starts empty when qBittorrent restarts, and its ids start again from 0 (seen on the playground: 33 before, 28 after). omaseed asks for lines after the last id it has seen (last_known_id), starts over when ids go backwards or the server comes back, and shows "no reason logged" when there is none (S4).

What the ones that show it agree on: the reason goes in the row's status text in red, a details field repeats it, and an empty value says so ("No errors", "OK"). Transmission keeps local errors apart from tracker errors, as omaseed already does (tracker errors have their own badge on the Trackers tab).
Nobody matches log lines to torrents. No qBittorrent front-end found does, and no qBittorrent issue or PR asks for the reason in torrents/info. Master (API 2.17.0, 5.3.0rc1) has no such field. Fix actions next to the reason are rare (only qBitController's Resume). qBittorrent #22134 says set location alone doesn't clear a disk-space error, which is why the block always offers p try again as well.

4 · the proposal

Say why, in plain words, where you already look

An errored torrent gets an error block at the top of its General tab: a plain headline, qBittorrent's own words, the file, when it was logged, and the actions that fix this cause. The STATUS row and the table's status cell carry the short version. Nothing changes for torrents that aren't errored.

5 · the wording

From the system's words to yours

The headline comes from the system's message at the end of the line (error: …), which is the same whatever language qBittorrent runs in. The second line keeps that message and says what libtorrent was doing, from the operation (file_open opening, file_write writing, file_read reading, mkdir creating the folder for, file_fallocate making room for, file_rename renaming, file_stat looking at). A message that isn't in the table keeps qBittorrent's words as the headline.

6 · building it

How it would be built

core

  • ServerLog: log/main?normal=false&info=false with last_known_id, polled only while a torrent is in error or missing files, and once more when one goes into either. It starts over when ids go backwards or the server reconnects.
  • TorrentProblem::parse(line): finds the quoted name, the file path, the hash prefix, the operation and the system message, without relying on the English words around them. match(problem, torrents): the hash prefix first, then the name, then the file under a save or download path. When it can't decide, it says so (S5).
  • Torrent gets problem (headline, detail, file, time, count, raw line, ambiguous). The table and the details read it.
  • QtTests: every line in §2, a French log, two torrents with the same name on 2.0 and on 2.1, ids going backwards, and a line for a torrent that's gone.

views

  • DetailsErrorBlock: the Kit Banner's language on several lines, with actions as clickable key hints. The table's Status delegate gets the short cause.
  • With D4 a, Notifier::notifyErrored, beside notifyCompleted, with the same click.
  • A spec line in REVIEW-v0.1.0.md: this adds to the General tab of the frozen v2 (Fig. 10) and the status cell.

checks

  • A new error-walk.sh: swarm.sh break error, then the block, the row and the notice in an omabox. Then m to a writable folder and p, and the block goes away. Then break missing for G3, and a playground restart for S4.
  • Live tests against :8081 and the strict :8082, since log/main needs the same login.
