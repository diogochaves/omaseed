Choosing a magnet's files before it starts

A .torrent in the add sheet shows its file tree, so you untick what you don't want before anything downloads. A magnet shows nothing, because it carries no file list: qBittorrent has to get it from the swarm first. Today you add it, let it start, and choose in the Files tab while it's already downloading. qBittorrent 5.2's torrents/fetchMetadata fetches that list without adding anything, and torrents/add then takes the choices with the magnet in one call. This board designs the wait: what the sheet shows while qBittorrent looks, when it calls the wait slow, what you can do meanwhile, and what is left behind on the server when you close the sheet.

The screenshots in §1 are real, and so are the API answers in §2 (the research on #44: qBittorrent 5.2.3, Web API 2.15.1, the offline swarm). The mocks use Theme roles only: use the theme switch below. The Public Domain Sampler's files and sizes are the swarm's. Other names and times are example data.

2 · what qBittorrent gives

fetchMetadata: ask, poll, get the list, add with the choices

POST torrents/fetchMetadata with source= a magnet, a bare v1 or v2 hash, or an http(s) link to a .torrent. While qBittorrent looks it answers 202 with the hashes. Once it has the metadata it answers 200 with the whole info dictionary. Its own Web UI asks again every second.

The result is kept per Web UI session. omaseed's QbtClient keeps its cookie jar and prefers the API key, so it sees the 200 as long as every poll goes through the same client. A client without a session gets 202 forever (diogochaves/upstream#86; that is why app-box.sh api never saw a 200 in #39).

Then, in the same session, torrents/add urls=<the magnet>&filePriorities=1,0,1 adds it with its metadata and the priorities already set. A skipped file is never created on disk. No stop, filePrio, start dance as for a .torrent (docs/11 D1).

3 · timing

When the sheet says what

The lookup starts as soon as one magnet is in the sheet (D1). The sheet asks again after 0.25 s, 0.5 s and 1 s, then every second, and every 5 s after a minute. Each 202 is a hash-table look-up on the server, so this costs nothing worth counting. A 200 at any point replaces whatever the FILES row shows with the tree.

At any point: a 200 → F2, the tree. On the swarm that's always inside the first segment. The time axis is not to scale.

The sheet never gives up on its own while it's open (D3). Stopping the polls wouldn't stop the lookup on the server anyway, and a list that turns up after two minutes is still worth showing. Every way out (§4) is there from the first second.

4 · the proposal

The sheet's states for a magnet

Everything above FILES works as today from the first moment: name, category, tags, Save to, limits, switches. FILES appears under the switches, where a .torrent's tree is, and holds either the wait or the tree. add works in every state: before the list is in, it adds every file, exactly as today (D4). The keyboard stays where you are when the tree arrives. Nothing new to learn: tab reaches the tree, and the tree's keys are T1's.

5 · closing during a lookup

There's no cancel. What a lookup left running costs

Every add of that magnet cancels its lookup, whichever button: qBittorrent's add calls its own cancelDownloadMetadata. So the usual paths leave nothing behind. A lookup is left running only when the sheet lets go of a magnet whose list hasn't arrived: cancel or esc, another magnet pasted over it, or the magnet joining a batch. A lookup that already answered 200 costs one cache entry in the session, until that hash is added or the session ends (an API-key session never ends).

7 · building it

How it would be built

core

  • QbtClient::torrentsFetchMetadata(source): 202 and 200 kept apart in the reply, any other status an ApiError. AddOptions gains filePriorities and stopCondition.
  • MetadataLookup: one lookup, its poll schedule (§3), its phase (waiting for the server, fetching, slow, may never come, got it, not supported) and elapsed time. On 200 it turns info.files into TorrentFileEntrys with the root stripped. QtTest with the research's bodies as fixtures: multi-file, single-file (path == info.name), pad files, 202 {} for a link, 404.
  • PrivateTrackers: the hosts of the library's private torrents, for F5. A table test.

app and views

  • App owns the one lookup the sheet shows, on the current server's client, and loads AddFilesModel from it. addTorrent sends urls plus filePriorities for a magnet, and stopCondition=MetadataReceived for "add stopped" before the list (D5 a).
  • AddSheet: showFiles covers a magnet with a list; a new AddFetchLine.qml draws F1, F3–F5, F7 and F8, with its tst_AddFetchLine.qml. A spec line in REVIEW-v0.1.0.md: this adds to Fig. 5 of the frozen v2.

checks

  • magnet-walk.sh grows, on an app-box.sh --qbt box so the playground stays put: the Sampler's magnet shows its tree inside a second; untick sampler.mkv, add, and torrents/files says 1/0/1 with no .mkv on disk. A swarm torrent's magnet (private) reaches F3 and F4 (with a test-only clock), and enter still adds it.
  • A live test against :8081 for the 200 shape (the Sampler is in its library, so it answers at once) and against :8082 for the API-key session.
