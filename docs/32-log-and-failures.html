qBittorrent's log, and the failures only it knows

When you move a torrent and the move fails, qBittorrent answers "OK", leaves the files where they were, and writes the reason to its log. A failed file rename, a web seed that answers 404 and a .torrent copy that couldn't be written work the same way. The torrent looks fine, so omaseed shows nothing. #54 already reads that log for errored torrents. This board proposes two things on top of it: show these other failures on the torrent they belong to (#55), and give qBittorrent's whole log a place in omaseed, the way the Web UI's View → Log does (#56).

Every screenshot in §1 and every log line in §2 is real: build c956e0f in an omabox against the :8081 playground (qBittorrent 5.2.3, libtorrent 2.1.1), with the failures caused on purpose and cleaned up afterwards. Names and times in the mocks are example data unless the caption says otherwise. Use the theme switch below: the mocks use Theme roles only.

Memory only, and it starts over. Each log keeps 20 000 lines (MAX_LOG_MESSAGES) and is empty again after a restart, with ids from 0. If omaseed asks with an old last_known_id after a restart, it gets [] until the new ids pass it. #54's reader already starts over when a full sync arrives (a restart always causes one). A library of 3 450 torrents writes one Restored torrent line each at start-up, about a sixth of the buffer.
The file on the server keeps more. With write a log file on (the default), qBittorrent also writes qbittorrent.log in the folder from T4, starts a new file past 65 KiB and deletes files older than a month (the playground has 54 of them). That file survives restarts, but only something running on the server's machine can read it. The API never serves it.
Translated, as #54 found. qBittorrent writes its part of each line in its own language. As in #54, omaseed reads the quoted segments and libtorrent's untranslated tail, never the English words around them. The level comes from type, which doesn't depend on the language.
Found on the way: a rename can overwrite another file. Renaming a torrent's file onto a name that exists on disk but isn't one of the torrent's files replaces that file silently: renameFile answers 200 and nothing is logged. Reproduced twice on the playground. Noted for triage, with the API gap (failures only in the log).

4 · #55, the proposal

The last failure, on the torrent, in yellow, until it's fixed or you dismiss it

A move, rename or part-file failure gets the block #54 made, at the top of General, in yellow because the torrent still works. It names what didn't happen and where things are now, with the actions that fit. When omaseed itself asked for the move or rename, the footer says so at once, the way it already does for a refusal. Web seed failures go on the HTTP sources tab, next to the URL. An export failure is about a setting, so it goes next to that setting.

6 · #56, the proposal

The log as the window's third face

qBittorrent's log is server-wide, its lines are long, and you read it now and then, often while following something as it happens. A third face beside library and seed gives it the whole width, and a key gets to it from anywhere, as ` does for the console. ~ opens it and ~ or esc goes back. The log is read from the server only while this face is on screen.

7 · building it

How it would be built

core

  • ProblemLine::parse learns the move, rename, URL seed, export, partfile and content-removal lines, in the same way as #54: quoted segments and libtorrent's tail, never the English words. The Kind enum grows to match.
  • ProblemLog also reads warnings while nothing is errored: every 15 s while the window shows, and every poll for 30 s after a move, rename or delete omaseed asked for. One warnings-only request with last_known_id is a few bytes when nothing happened.
  • A torrent's model row gets failure beside #54's problem, worded from §5. It clears on the "goes away when" signals in §5 and on a dismissal, which is stored in state.json per server as id plus timestamp plus a hash of the line.
  • ServerLog, new: log/main with all four levels, kept only while the log face is open, 20 000 lines at most (the server's own limit). It starts over when ids go backwards or a full sync arrives. LogFilterModel handles levels, words and the torrent chip.
  • QtTests: every line in §2, a French log, a rename failure on two torrents of the same name, a restart (the old last_known_id answering []), dismissals across a restart of omaseed.

views

  • DetailsErrorBlock takes a warn kind and a dismiss action; a torrent can show the error and the failure, one under the other. x dismisses in General only; in Files it still skips a file.
  • DetailsWebSeedsTab gets a status line per URL. Settings → Downloads gets the export note.
  • LogView.qml is the third face, its keys an area of their own in Keymap.qml (~ global). Kit/Chip serves as the level chips.
  • The footer note for actions omaseed asked for goes through App.actionFailed, as refusals do.
  • A spec line in REVIEW: General, the HTTP sources tab and the header's faces change from the frozen v2.

checks

  • failure-walk.sh in an omabox with the box's own qBittorrent (app-box.sh up --qbt), so nothing outside the box is touched. A move out of a read-only folder shows N1 and then F1. Making the folder writable and pressing m clears it. A rename into a read-only folder shows F2, a web seed on a local 404 server shows W1, and a read-only export folder shows E1.
  • The same walk opens ~, filters to warnings, uses t, y and G, and restarts the box's qBittorrent to check that the face starts over.
  • Live tests against :8081 and the strict :8082, since the log needs the same login.
