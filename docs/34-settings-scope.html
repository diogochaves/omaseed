Settings: whose settings, which backup

Settings has two groups: omaseed's own, and qBittorrent's, which edits one server at a time. Testing the 0.2.0 package, you found that nothing says which is which. Both groups end in a pane called Backup. The server's name above the qBittorrent group is a switch, and nothing says so. Settings move from one server to another only through a file. This board shows what omaseed does today, then proposes how each pane names its scope, how the server switch looks and what its keys are, whether to copy settings from server to server directly, and whether the file extensions stay as they are.

Every screenshot in §1 is real: build 9d1858b in an omabox (Omarchy 4.0.4, 1920 × 1080, theme baseline) with two qBittorrent 5.2.3 of its own, public on :8090 (one torrent) and private on :8091 (four), the second added in Settings › Servers. The file facts in §6 come from the files that run wrote. The mocks use Theme roles only: switch the theme in the bar below.

1 · where we are

Today: two Backups, one quiet switch, and the same words for both groups

What that adds up to

  1. Two panes named Backup, with the same glyph, nine rows apart in one nav. Which is which depends on a dim group caption.
  2. omaseed's Backup never says torrents are elsewhere, and only its third row mentions that it carries qBittorrent settings.
  3. The server's name is dim, small text under a caption. It is the one control in the nav that switches something, and the nav draws it like a label (T3, T4).
  4. A switch in Settings switches the app (T6). The library, the tray and the default server all follow. That is right under C8 (one connection), but nothing in Settings says so.
  5. The Backup pane's rows don't say whose. The head names the server on the right, in dim text. The rows, the import sheet's "from" line and the picker don't.
  6. Copying settings between servers takes three steps and a file, and the preview doesn't say which server the file came from (T9).
  7. The files are tars and JSON under omaseed's own names. No MIME type is registered, so the desktop calls the two archives "Tar archive" (by their ustar magic) and the JSON "Program" (§6).

D4 a, keys (recommended). s keeps going straight to the next server, as today and as servers-walk checks, and works in every qBittorrent pane. The footer says s next server in every one of them, Backup included (T5). A click on the select, or enter on it from the nav, opens the list: j k move, enter switches, esc closes. Cycling stays one key for the usual two servers, and the list covers three or more. D4 b: s opens the list instead, so s enter switches. That is safer with many servers and slower with two.
D5, the words after a switch. The footer's note line says omaseed is on private now · the library too, as other actions report in the footer (M16). The panes read private's settings again (as today). The list's last line says so before you pick.
Why the switch stays app-wide. Editing private's settings while the library stays on public would need a second live connection that writes, and C8 (one connection) and board 16 ("nothing is ever copied from one server to another behind your back") rule that out. A switch from Settings is the same switch as the rail's SERVERS group and Settings › Servers' d. This board only makes it say so.
5 · point 4 · D6

Copy settings from another server

Today it's export on A, switch, import on B, then delete the file (T9). There are two direct ways, and both end in the import preview that already exists (D2's second sheet), so nothing changes before you see it. The copy always goes into the server omaseed is on and only reads the other one, so C8's rule that the pane acts on the connected server still holds.

Recommended: D6 a, with b as its fallback when A can't be reached. It matches how people think about this ("make public like private"), it never moves the library, and the second client is one omaseed already makes for the server sheet's test. Between two servers on one machine, most differences are machine-specific and start unticked, as T9 shows. The copy is most useful for categories, tags, RSS rules and the seeding and queue limits.
Not offered: copy to another server. Pushing into a server omaseed isn't on would write through the second client, and a Web UI or port change could cut a server you aren't watching. Switch to it first, then copy from.

A custom extension on a standard container is the usual pattern. .odt, .docx, .epub, .kra and .jar are zips under their apps' names. Arch's own packages take the other route, .pkg.tar.zst: the app's name first, then what any tool can open. Both work. The custom name says "open me in omaseed", and the double name says "this is just a tar". What's missing today is the step the zip-based formats take: a MIME type, so the file manager shows "omaseed backup" with omaseed's icon instead of "Tar archive".

D7 a: keep the names. Ship data/io.github.diogochaves.omaseed.xml (shared-mime-info) with application/x-omaseed-backup (*.omaseed) and application/x-omaseed-torrents (*.omaseed-torrents). Each is sub-class-of application/x-tar, so archive tools still list them under "Open with". Install it in share/mime/packages; Arch's shared-mime-info pacman hook rebuilds the database, and update-mime-database covers a cmake --install into ~/.local. Files made before keep working, since the names don't change.
D7 b: .omaseed.tar, .omaseed-torrents.tar. Any tool opens them by name, and no MIME file is needed. But a double click opens an archive manager, not omaseed, and an extracted copy edited by hand gets restored as-is. omaseed would read both names from then on.
D7 c: keep everything as it is.
The settings stay .json in every option: one readable object, opened in an editor, and the format named inside it. With D7 a, a JSON file could also get a magic rule on "format": "omaseed-qbittorrent-settings", but key order isn't fixed, so the board leaves that out.

The name never decides. Every reader already checks the manifest's format and version and refuses another app's file, or a damaged one, before anything changes (board 24 §7). Under D8 a, a renamed file still opens from "All files". D8 b leaves the filters as they are.
D9, a double click. With D7 a, omaseed could list both types in its .desktop MimeType= and open Restore or Import torrents on the file it's handed, as it does for .torrent. Recommended: D9 a, not now. Restoring is rare and deliberate, an import needs the right server connected first (D2), and Settings already offers both. D9 b: yes, through the same sheets.
7 · building it

What the recommended set changes

Views. SettingsModal: omaseed Backup's head and scope line, its t link, and the captions (D1 a). qBittorrent Backup's scope line, row titles, footer s hint and copy row (D2 a, D6 a). The nav head becomes the Kit's pick-one select with a server list (D3 a, D4 a). QbtImportSheet: title and "from" line from the file's server, or "Copy settings from X into Y".
App and core. collectQbtSettings reads through a given client. A short-lived client for another server, as testServer makes, signs in from the keyring. With D7 a: data/io.github.diogochaves.omaseed.xml, installed by CMake and the PKGBUILD, and the import settings filter (D8 a).
Checks. A backup-walk.sh step copies private's settings into public with no switch, checks the hero still says PUBLIC, and compares the changed keys on both servers. A servers-walk.sh step opens the select and switches with enter. qml tests for the select's one-server and three-server cases. In a box, gio info reads the new types.

Once ruled: DECISIONS entries for D1–D9, the CHANGELOG lines, and REVIEW §-lines for what departs from board 24. Board 24 and v2 stay as they are.
