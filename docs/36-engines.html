Engines beyond qBittorrent

omaseed today is a qBittorrent client all the way down. #60 asked about Deluge; a second comment asks for Transmission. This board proposes how omaseed becomes the torrent frontend on Omarchy, whatever engine sits behind it, without qBittorrent losing anything. It covers where the code stands, how other multi-engine clients are built, what each engine's API can do, the design that follows, the order of the work, and the calls that are yours.

Facts come from an audit of main at 8c97d45 and two research notes (prior art and engine APIs, with source links) kept in .local/docs/engines/. Flood, Transdroid, Sonarr, Electorrent, qui and Tremotesf are GPL: read for design only, nothing copied.

Tied to qBittorrent

  • Sync is qBittorrent's delta protocol. SyncEngine::applyData reads rid, full_update, *_removed and server_state, and finds completed torrents in the raw diff. Peers sync the same way.
  • Models take API JSON. Torrent::applyJson returns changed qBittorrent key names, which TorrentModel turns into roles. M12's pending values are keyed by seq_dl, auto_tmm and the like. GlobalState, the category, tag and tracker models and every details model take the wire shape.
  • Wire sentinels inside typed fields: ETA 8640000, limits −1/−2, file priorities 0/1/6/7, ratio 9999, the ** [DHT] ** pseudo-trackers.
  • Preference keys outside the settings pane: AltSpeed, AltSchedule, StatusWriter, App and MainView.qml read dl_limit, scheduler_*, save_path, web_ui_port.
  • qBittorrent-only surfaces: the settings pane (1,625 lines, 194 keys), settings export and import (C8), the log face (C3), the problem log (C2), metadata before the add (C5), the first-run detector.

Already engine-neutral

  • Torrent is a typed struct, and the table filter, the rail counts, the seed console and ledger, the status digest and every QML view read its typed fields and roles, never JSON. No raw state string reaches QML.
  • Server, ServerStore, SecretStore, CertificatePin and PathMap work for any engine. Server just has no field saying which engine.
  • Parsing (Bencode, TorrentFile, MagnetLink), renames, library match, shared data, free space, backups' tar, theme, tray, notifications, the bar widget.
  • QbtReply and ApiError are a generic future and error value under a qBittorrent name.

A bridge that makes one engine speak another's APIReflection (Transmission RPC on qBittorrent)The client doesn't changeMissing fields come back as template values. Nothing serves qBittorrent's /api/v2 on Transmission or Deluge, and writing it means pretending to be qBittorrent forever (#60's option 2).

Two details carry over directly. Electorrent makes the deltas part of its interface (all, changed, deleted), so qBittorrent's maindata passes through untouched, and its feature record carries values, such as which file priorities an engine accepts. Tremotesf, a Qt Transmission client, polls a field list that depends on the version and runs a generic differ that hands Qt models removed and changed ranges. That is the piece omaseed needs for engines without real deltas.

4 · the proposal

One model shaped like qBittorrent's, a feature record per server, deltas as the contract

The second pattern from §2, built for depth. qBittorrent stays the reference: the internal model is its model, written in omaseed's own terms, and another engine fills what it can. The views read what the server can do, never which engine it is.

1 · The neutral model

  • Torrent::apply(const TorrentPatch&) replaces applyJson. A patch is typed fields plus a mask of the ones present; the change set is a field enum, not key names. M12's pending values use the same patch.
  • Sentinels go at the edge: "no estimate", "unlimited" and "global" become explicit values; a field an engine doesn't have is absent, so a view can hide it rather than print a zero.
  • A torrent's id is its info-hash everywhere. Transmission's integer ids stay inside its engine.
  • State becomes a phase (downloading, seeding, checking, moving, metadata, stopped, errored, missing) plus flags (stalled, queued, forced), and the engine's own state word is kept for details. The rail groups are derived in one place, so Q16's rules survive word for word for qBittorrent.

2 · Sync

  • Every engine hands SyncEngine a SyncDelta. qBittorrent's maindata converts 1:1, so it keeps its deltas and its cost.
  • Transmission returns whole objects for torrents active in the last 60 s, plus removed ids. They go through SnapshotDiffer, so only real changes reach the roles. A gap longer than 50 s (hidden, asleep, lost) asks for a full list.
  • Deluge through deluge-web and any rTorrent use full polls and the same differ.
  • Completion, lost and back, and the cadence (1.5 s / 5 s / 15 s) stay in SyncEngine, computed from neutral fields.

3 · The feature record

  • EngineFeatures is resolved after the probe, from engine and version, as supportsFetchMetadata and supportsShareLimitAction already are. It is never a fixed list per engine.
  • It carries values, not only yes or no: how a server groups torrents (categories with paths, one label, many labels), which file priorities exist, which share-limit actions, queue or not, stop or pause.
  • Menus, the palette, the keymap, the ? sheet, the add sheet, the limits sheet and the details tabs read it. A missing feature is never a button that fails.

4 · What stays qBittorrent's

  • The settings pane, settings export and import, the log face, the log-based problem log, RSS counts: kept as they are, behind the feature record, reached through the qBittorrent engine.
  • "Why it errored" (C2, docs/28) gets easier elsewhere: Transmission and Deluge put the reason on the torrent, so their engines fill it directly.
  • New features are designed against qBittorrent first and switched on per engine when it can. Another engine never holds a qBittorrent feature back.
Servers. Server gains an engine field; servers.json goes to version 2 and every existing entry becomes qBittorrent. Sign-in modes become per engine: qBittorrent keeps API key, cookie and none; Transmission gets Basic or none, with its session-id header handled inside the client; Deluge gets a password. The status file the bar widget reads gains server.engine next to server.version, an addition to docs/20's contract.

6 · the order of the work

Two steps that change nothing you can see, then Transmission

Each step is its own issue, lands on main and ships. qBittorrent behaves the same after E1 and E2, and the walks prove it before any Transmission code is written.

QbtEngine holds the only qBittorrent-to-neutral translation.done when ctest is green, recorded maindata fixtures from :8081 give the same rows, roles and rail counts as before, and swarm-walk and actions-walk shots match main.

E3medium

8 · risks

What could go wrong, and what holds it

  • A qBittorrent regression during E1 and E2. Recorded fixtures compared row for row, the walks before and after, no behaviour change allowed in those steps.
  • Testing twice from now on. Live tests per engine run in their own ctest label; recorded fixtures keep unit tests offline. CI stays -LE live.
  • Transmission's protocol moves again (4.1 renamed everything). One dialect only, 4.1 and later, checked against rpc_version_semver; older daemons are refused with words that say why.
  • Scope. E1 and E2 together are the size of a release. They are worth doing even if Transmission waits: App stops talking to a wire format, and the models get easier to test.
  • The detector's contact rule. Today the first-run detector only probes ports (the rule that keeps agents off a real library). Recognising an engine by its answer means an HTTP request: E8 below.
