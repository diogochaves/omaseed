Engines in the window

Board 36 settled how omaseed drives engines other than qBittorrent and left the window to this board. Every word in today's window assumes qBittorrent: the first run asks "which qBittorrent", a Transmission address fails its test with a 409, and the rail, menus and settings are qBittorrent's. This board draws where the window learns a server's engine, where it says it, and what it does with what an engine can't do. For a qBittorrent server nothing changes except the engine's name in two more places.

§1 has real screenshots of today. §2 onwards are mocks at base 14 in Theme roles at Q19's 4.5:1 floor; the theme switch repaints them. The second server is seedbox: Transmission 4.1.3 on a VPS behind a reverse proxy, the setup #85's requester described. Deluge appears where it behaves differently. Each open question is a numbered call (W1–W16) in §9, with a recommendation.

2 · first run (C14 E8)

The detector names the engine; the address is checked only when you pick it

E8's contact rule stands: the detector connects to ports and reads local hints (running processes, config files), and never sends an HTTP request. What it adds is the other engines' ports and hints, so the row it offers can say which engine it found. Picking the row (or testing a typed address) is the first request, and it is what confirms the engine.

ports
TCP connect only: 8080 (qBittorrent), 9091 (Transmission), 8112 (deluge-web).
processes
qbittorrent-nox, qbittorrent; transmission-daemon, transmission-gtk, transmission-qt; deluged, deluge-web.
config
qBittorrent.conf (WebUI\Port, as today), transmission-daemon/settings.json (rpc-port, rpc-url), deluge/web.conf (port).
naming
A process or config names the engine. A bare open port names its usual engine and says "probably".
a desktop app
As today for qBittorrent's Web UI being off: transmission-gtk with remote access off says "turn on Edit › Preferences › Remote"; deluge-gtk in classic mode says it has no web server (Deluge needs deluge-web).
several
One row per engine found (W2), in the order qBittorrent, Transmission, Deluge. Q26 still holds for two of the same engine: one row, and the done step points at Settings › Servers.
install
Stays qbittorrent-nox: qBittorrent is the reference engine (W3).
3 · add a server (C14 E8, #85)

Recognised on test, with the engine shown and overridable

The same form serves the first run's sign-in step and Settings › Servers › add a server. It gains one row, engine, between URL and auth. It starts on recognise: the test asks the address in the engines' own ways, one unauthenticated request each, in an order taken from the address (W5), and stops at the first that answers as itself. The chip then says what it found. Picking an engine instead tests only that engine (a proxy that hides the tell-tale answer).

For recognise-on-test (W4 a). People paste the address they use in a browser; most don't know which API sits behind a seedbox's web page. The test was already the moment omaseed learns the version (T3), so the engine comes with it. The chip makes the result visible and lets a proxy setup force it.
Against. Up to three requests to an address that isn't a torrent engine at all, each with C10's timeout: a wrong address can take three times as long to fail. The order from the address's hints keeps the usual case to one request.
4 · the server line, and where else the engine is named

Named wherever you look at one server; left out where you pick between them

The hero's server line already says "QBITTORRENT 5.2.3" (T5). A Transmission server reads the same way: SEEDBOX · TRANSMISSION 4.1.3 ▾. While a server is down, C12's state words take the place of the engine and version, as they do today. The rest follows one test: where you are looking at one server, its engine is named; where you are choosing between servers by name, it is not (W11).

5 · labels (C14 E5) and what a Transmission server leaves out (E4)

Each group keeps its place and its keys, and takes the engine's word

E5 is ruled: one-per-torrent groups use the categories section, many-per-torrent ones the tags section, each called what the engine calls it. Drawn, that means the section keeps its place in the rail, its glyphs and its keys; only its heading and the matching words in the add sheet, the menu and the palette change. Transmission's labels (many) sit where tags do; Deluge's Label plugin (one) sits where categories do. No engine has both, so "labels" is never on screen twice.

Per-torrent limits at add: Transmission's torrent_add takes none, so the engine sets them with torrent_set right after the add, and the fields stay. Assumed here; E4 confirms it on the playground.
6 · details an engine can't fill (C14 E4)

The tabs stay put; what is missing says so in one line

E4 is ruled: a details tab the engine can't fill says so in one line. Drawn, the four tabs keep their places and their keys 1–4 on every engine, so muscle memory survives a server switch. Inside General, a row whose field the engine doesn't have is left out (E1 made such fields absent rather than zero), so nothing reads "—" for a fact that simply doesn't exist there. A part of a tab that the engine fills only partly keeps what it has and adds one line under it.

7 · the shared settings (C14 E6)

A page of basics in the engine's own group, which E5's pane later replaces

E6 is ruled: Settings › qBittorrent stays as it is; another engine gets its own smaller pane after it works, and until then "the shared part sits on the server's page". The shared part is what every engine has: the listening port, global limits, alternative speeds with their schedule, the default save path. Two readings of "the server's page" are drawn. The recommendation (W14 a) is a page in Settings, in a group named after the engine, built exactly like the QBITTORRENT group (C11's server select, saved as you change it), so E5 only adds sections to a group that already exists. Option b puts the same rows in the server's sheet.

For the engine's group (W14 a). Settings already has one shape for "this engine's settings, for the server you pick" (T11); a second engine uses it too. The sheet stays about connecting (address, sign-in, path map, test). The quick sheets (→ speed limits, Burst) work as today on any engine, through EngineClient's global limits.
Against. It reads E6's "server's page" as a page in Settings rather than the server's sheet, so it is flagged in W14. With one Transmission server, Settings shows a group with a single page until E5.

board 40 · the frame

The same proposals hold in board 40's frame

Board 40 (not ruled) recommends frame A: a sidebar that navigates, the servers at its foot, a status line at the bottom, keys shown on demand. It lists "room to grow" for engines among its needs. This board is drawn in today's window because that is the ruled one; nothing here depends on the hero staying where it is. If frame A is ruled:

  • The server line moves with the server into the status line: "seedbox · Transmission 4.1.3". W10 and W11 apply there unchanged.
  • The views become the rail's first rows (library · seed · log); on Transmission the log row is gone, as the tab is here.
  • The labels sections are rail sections in both frames; W12 doesn't change.
  • The notice spans the content instead of the window (board 40's change to docs/35); the engine's error words (§4) are the same.
  • Keys on demand (board 40's K3) makes W16's footer line more useful, since a hidden key is never painted in the first place.
10 · what changes

Against the rulings, and what each step builds

Rulings it touches

  • docs/14 (first run): the welcome line, step 1's heading and the "nothing found" line name the engines omaseed drives (W3).
  • Q26: one row per engine found; Q26's "one row, more in Settings" stays per engine (W2).
  • C10: the test also recognises the engine; "save anyway" is not offered for a version omaseed refuses (W8).
  • C11: the server select of each engine's group lists only that engine's servers (W15).
  • C12: the error words name the server's engine (board 36 §7 already said so); its state words still replace the engine on the server line (W10).
  • C14 E6: "the server's page" read as a page in Settings (W14, flagged).

Unchanged

  • Every qBittorrent screen, except the engine row in the server sheet and the engine in Settings › Servers' rows.
  • C14 E4's rule (hidden where offered), E5's sections, E7's qBittorrent-only features.
  • Q27's certificate pin for every engine; its HTTPS warning stays qBittorrent's.
  • The seed console, the ledger and the weekly recap: they need only uploaded, downloaded, added on and all-time totals.

Which step builds it

  • E3 (#84): §2 and §3 (detector, engine row, recognition, per-engine sign-in), the engine in §4's places, servers.json v2. A recognised engine that isn't driven yet is refused in words (W9).
  • E4 (#85): §5 and §6 on a live Transmission, the footer line and the ? sheet's foot line (W16), the TRANSMISSION group with its basics page (W14).
  • E5 (#86): Settings › Transmission replaces basics; the welcome line names Transmission.
  • E6 (#87): the same for Deluge.
  • Tests: tst_ServerSheet.qml (engine chips, auth chips per engine), the detector's unit test (ports and hints per engine, no HTTP), servers-walk.sh with a Transmission address.
