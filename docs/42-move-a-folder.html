Move a folder

Moving a whole folder of the library to another drive, as one job that can run for two hours. You pick the folder, not a selection. Every torrent keeps its place below the folder, nothing is sent until a preflight has checked room, writability, shared data and the files no torrent owns, and the job runs in waves you can pause. It survives a hidden window and a restart, and ends with one summary.

§1 has real screenshots and what qBittorrent 5.2.3 does, measured on the playground. §2 onwards are mocks at base 14 in Theme roles, at 1180 px; use the theme switch for them. The examples are made up: a server "home", folders under /srv/media, /mnt/archive and /mnt/fast. The calls are M1–M20 in §13; at the ruling they become one C entry in DECISIONS, not the manual pass's M numbers.

theme
1 · today

A move is a selection sent to one folder, then forgotten after 30 s

Set location (m, docs/27, #28, #41) works for a handful of torrents. Moving a whole folder runs into what it never had to do: find the folder, keep the folders under it, check the drive, follow a queue for hours, and deal with files no torrent owns.

qbittorrent-nox 5.2.3, Web API 2.15.1, the playground on :8081, 2026-10-18. Every torrent was put back where it was and rechecked.

2 · pick a folder

The library's folders, in the rail

A folders group in the rail, after categories: the save paths the library uses, as a tree. Picking one filters the table to it and everything below it, the way a category does. A scope line above the table says what is picked and offers the move. shift+m moves the picked folder (m stays set location), and so do the row's menu and : "move folder…".

3 · the move sheet

Where to, what goes where, and a preflight before anything is sent

One sheet. The field holds the folder's new path, prefilled with its current one; browse picks a parent and the sheet appends the folder's name. Under it, every save path in the folder and where it goes, then the preflight, read again whenever the field changes. The move button says how many torrents it sends. Nothing is sent before it is pressed.

Writability is checked as this machine's user. When qBittorrent runs as another user (a container with a different uid), the check reads the owner of the folder's files and tests that owner's write permission, which can still be wrong both ways. So the first torrent, the smallest one, is always sent alone, and nothing else is sent until it has landed or failed (M6).
4 · the job

A band under the hero, for as long as it runs

A running move is a band under the hero, in board 35's box (C12, docs/35 N1–N2) in the accent kind, with a 2 px progress line on its bottom edge. It stays while the job runs, through every view (library, seed, log). Its actions: pause, show (the job's torrents in the table, with a Move column) and details (the figures and the log lines it has read).

Waves

first
The smallest torrent, alone. It is qBittorrent's answer to "can you write there". If it fails the job pauses with its reason before anything else has moved.
then
Smallest first, keeping 3 in qBittorrent's queue: one moving and two behind it, so qBittorrent never waits on omaseed. qBittorrent moves one at a time anyway, so this costs no speed.
between
Before each send, free space is read again (on this machine, or qBittorrent's figure when the destination is its default drive). A torrent that wouldn't leave the low-disk threshold (Q16, 2 GiB by default) is not sent; the job pauses and says so.
landed
A torrent has landed when the sync shows its save path at the target and it isn't moving. That works in any language. The log adds the failures and which torrent is moving now.
time left
The bytes still to move, over the speed of the last 10 min of landings (bytes on disk of the torrents that landed). When omaseed sees the destination, the growth of the current torrent counts too. Same-drive moves are renames: the band says "renaming", with no time left.
saved
~/.config/omaseed/moves/<server id>.json: the target, each torrent's old and new save path and its state, the loose files' list. Written on each change, at most once a second. Kept after the end until the summary is closed.
5 · when it goes wrong

Failed, stuck, full

For moves made by a job, the log is read on every poll for the job's whole life, not 30 s (changes C2 D2 for jobs only; set location keeps D2). A failed torrent doesn't stop the job: it is marked, counted in the band, and gets C2 D1's yellow block in General as today. Two failures stop it: no space left, and the first torrent failing.

One summary, one notice, the failures one click away

7 · loose files

Carried after the torrents, never deleted

When the preflight's tick is on (on by default when omaseed sees the server's disks), the files no torrent owns are carried right after the last torrent lands. omaseed does this itself, on this machine: qBittorrent has no API for files it doesn't own.

which files
Every file under the folder that is under no torrent's content path, and none of the files of a torrent added without a subfolder (its file list is read for that). Matching on the content path avoids the false positive qui fixed in April 2026, where only the save path was used.
never loose
A visible list, shown in the preflight: .parts and *.!qB (qBittorrent's, they belong to a torrent and move with it), Thumbs.db, desktop.ini, .DS_Store.
too recent
Changed in the last 15 min: it may still be being written. It stays, and it is listed.
unreadable
A path that can't be read is unknown, never loose. It stays and is listed. This is the lesson from qbit_manage #1379.
how
Same drive: a rename. Another drive: copy to a temporary name beside the target, hashing as it reads, then read the copy back and compare. Only then rename it into place and remove the source. The copy keeps the file's time.
already there
The same size and hash at the target: it counts as carried, and the source goes. A different file: both stay, and it is listed. Nothing at the target is ever replaced.
after
Folders left empty at the source are removed, only when empty. Anything else stays.
can't see
No path map and no local view (S3): there are no loose files to show and nothing is carried. The summary says files may have stayed behind and that a path map lets omaseed see them.

9 · edge cases

What the sheet and the job do

casewhat happens
destination inside the folder (games → games/new)The move button is off: "That is inside games."
destination is the folder itselfOff: "games is already there."
a torrent already at its targetSkipped and counted ("3 already there").
destination on the same driveA rename for each torrent; no room needed; the band says "renaming" and gives no time left.
a different file at a torrent's targetThat torrent is left out and listed (§1, upstream#123). The rest go.
a torrent outside the folder whose files are all inside it (added without a subfolder one level up)Pulled in and named in the preflight; it moves to the matching place, the parent of the new path.
a torrent outside with only some files inside (spanning the folder)Not pulled in. Listed: "spans games: its files inside would be left without it". Moving the folder's other torrents is still allowed.
torrents still downloading, or with an incomplete folderIncluded. qBittorrent moves what is there and goes on downloading at the new place. With "keep incomplete in", the data in the incomplete folder stays put and goes to the new save path when complete. Assumed: check on the playground before the build.
a torrent added to the folder during the jobNot in the job; the summary names it ("1 added during the move is still at /mnt/archive/games").
a torrent removed during the jobDropped from the job and counted as removed.
switching server during a jobThe switch asks: the job pauses until you are back (C12: no requests to a server the app isn't on). The servers block reads "home · move paused".
a second move while one runs (on the same server)Its sheet runs the preflight and offers "move after games"; jobs run one after the other. Another server can run its own job; its band shows when that server is open.
qBittorrent restarts mid-jobThe server is lost (docs/35 band) and the job band says "waiting for home". When it is back, torrents not at their target and not moving are sent again.
a torrent's category changes (automatic management) during the jobqBittorrent moves it itself. The job marks it "moved elsewhere" and doesn't fight it.

11 · how it's built

Core first, then the views, proven on the playground

FolderTree
src/core: save paths to nodes (count, bytes on disk from completed), the rail's model and the scope line's figures. Pure, with a QtTest: nesting, a drive's top, trailing separators, case.
LooseFiles
src/core: walks a folder on this machine against the torrents' content paths and file lists, applying age, the never-loose list and fail closed. Its own QtTest with a fake file system. Built so a later "files no torrent owns" view (per folder, outside a move) can use it as it is.
MovePlan
The preflight as data: each torrent's target, skips, collisions (needs the local view), sharers through SharedData, room through FreeSpaceProbe, auto-managed ones. Pure, tested.
MoveJob
Beside ProblemLog, fed by SyncEngine::synced and the log read. States queued, moving, moved, failed, stuck; waves; pause, end, resume; time left; saving and restoring its file. QtTest with a fake clock and a fake server.
LooseCarry
Copy, hash, read back, compare, rename, remove, on a worker thread with progress. Tested on a temp dir, including an unreadable file and a target that differs.
QbtClient
On main, as today: torrentsSetLocation (already one POST with hashes joined by |). New: 400/409/403 read as move words, not auth. Fake-server tests for a multi-hash body and each code. ProblemLog's watch gets a lifetime mode for a job.
engines
MoveJob takes neutral events (landed, failed with a reason, moving now) from a small feed. On main the feed is QbtClient plus the log parser. When main next goes into engines, the feed sits behind EngineClient with a feature flag (a move feed), as E2 did for the qBittorrent-only surfaces.
views
Rail folders group (RailGroup), ScopeLine, MoveSheet (beside LocationSheet), the job band (Kit/Notice in the accent kind plus ProgressLine), the Move column, the quit confirm. Each Kit change ships its tst_*.qml.

Proving it

  1. move-walk.sh, in an omabox with the box's own qBittorrent (app-box.sh up --qbt): a few hundred small generated torrents in two folders (one with a subfolder save path), loose files beside them, one partial torrent, one collision, destination on a tmpfs.
  2. In that walk: kill omaseed mid-job and start it again (J4). Run once with an unwritable destination (T2) and once with a tmpfs too small (T3). Check on the server and on disk that every torrent is at its target, the loose files arrived and match, and nothing at the source was lost.
  3. ctest with the new QtTests, and ctest -L live against :8081 and the strict twin :8082.
  4. A build and a checklist for Diogo. Agents never touch his real library: he runs these himself with his installed omaseed. First a dry run on a small folder (3 torrents, 1 loose file). Then the two real moves, each after a copy of qBittorrent's config is set aside (outside omaseed). Each ends with no torrent in error or missing files, the loose files at the destination, and df on both drives.

What this opens up

  • Files no torrent owns, per folder, as a standing view on a folder (list, keep, carry elsewhere): LooseFiles as built here.
  • A dry run for every bulk action, the way this preflight works: a DECISIONS principle rather than a board.
  • Recheck smallest first, then resume as a general action for torrents in error or missing files (E3's sheet).
  • Editing a category's save path, so automatic management can follow a move.
  • A server-side folder browser (app/getDirectoryContent) for servers omaseed can't see.
  • Recoverable delete, "gone from the tracker", and a category suggested from the folder. Ideas for their own boards.
