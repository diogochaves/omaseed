Skipped files and the disk

Skipping a file in qBittorrent stops it downloading. It does not take back what is already on the disk, and on an NTFS disk under Linux's ntfs3 driver (or exFAT, or FAT) that can be the file's whole size. A three-second misclick on 21 October left 80 skipped files holding about 78 GB on a disk with 23 GB free. This board proposes five changes. Two fix what happened: omaseed shows what skipped files still hold and frees it, and it holds back a big selection for a moment so a misclick can be undone. Two help around it: name the disk's driver where it changes what a tick costs, and say "isn't answering" when qBittorrent is only slow. A third, suggesting an incomplete folder, is dropped (D10, ruled); in its place a small notice for a move that never arrived (D13).

§1 is what happened, with the measurements behind it. §2–§6 are the proposals, mocks at base 14 in Theme roles (use the theme switch). File names in the mocks are made up; the sizes are the real case's. The three questions the first draft left open are answered and folded in: #115 (the recheck error is a libtorrent bug with hybrid torrents), #116 (what each filesystem does), #117 (an incomplete folder and open files). The calls are D1–D13 in §8; at the ruling they become one C entry in DECISIONS.

1 · what happened

One folder wanted, the whole torrent written

A torrent of 174 files was added from the add sheet with one folder chosen. The add sheet adds it stopped, sends the choices, then starts it, so nothing else was ever wanted at that point. Later, in the Files tab, a misclick wanted the whole torrent. It was skipped again within seconds.

85.8 GBon disk for the torrent: all 174 files at full size
8.0 GBwanted: 94 files
77.8 GBheld by the 80 skipped files
≈ 33 MBdownloaded when the files were written: 4 pieces of 8 MiB
23 GBfree on the save disk: NTFS through ntfs3, 15 TB, a spinning drive

Then the same steps were repeated on the playground qBittorrent (5.2.4, libtorrent 2.1.2), saving to a folder on another NTFS disk (the in-kernel ntfs3 driver), with a 113-file test torrent:

casestepsfiles on diskspace usedwanted

BEvery file wanted for 3 s after adding, then skipped43114.6 MB25 KB
C (the real case)Added with 4 files, finished, every file wanted for 3 s, then skipped113124 MB25 KB
C, then freedStop, delete the skipped files, start448 KBhealthy
B, then freed with a recheckDelete the skipped files while running, force a recheck448 KBerror, stuck (#115: libtorrent, hybrid torrents)
  • The tick itself takes the space. Wanting a file makes libtorrent open it for writing, and its first open sets the file to its final length, even on a stopped torrent with nothing downloading. On ntfs3, exFAT and FAT32 that allocates the whole file at once, and skipping it later keeps it. On the newer in-kernel ntfs, ext4 and btrfs the same file is sparse and costs nothing until data lands. ntfs3's prealloc option is not the cause (§4, #116).
  • The stall is NTFS's valid-data rule. Reserving the space is instant; the first write near a file's end makes ntfs3 write zeros over everything before it. On the NVMe that was 4.3 GB of zeros for one 16 KB write; on a ~150 MB/s spinning disk 86 GB is about ten minutes, which is the stall above.
  • qBittorrent never removes a skipped file, and its Web API can neither see the files on disk nor delete one. Only something that can see the disk can free that space, and omaseed sometimes can.
  • Stop, delete, start frees it cleanly. Delete, then recheck errored because of a libtorrent 2.1.2 bug (#115): on a hybrid (v1+v2) torrent, deleting a file whose pieces were downloaded and then rechecking fails with torrent_inconsistent_hashes. The test torrent is hybrid, and B had downloaded pieces of the deleted files. The misclick case, where no skipped piece was downloaded, stays clean even with a recheck. qBittorrent neither logs this error nor exposes it: the API only says error. Only removing the torrent (keeping files) and adding it again clears it.
  • omaseed did nothing wrong here. It sent each change at once, as N1 says it should. The cost came from qBittorrent and the disk, and omaseed is the only place it could be shown.
2 · proposal 1 · both kinds of disk

Skipped files that still take space, and one action to free it

The Files tab already lists every file with its priority. When omaseed can read the torrent's folder (the same rule as the add sheet's free space, below), it also looks at each skipped file on the disk. A column shows what each one holds, and the footer gives the total. The figure is the space the file really takes (its allocated blocks), not its listed size, so on a sparse disk (ext4, btrfs, the newer ntfs) a misclick shows the next to nothing it cost, and on ntfs3, exFAT or FAT it shows the whole file.

Skipped files that hold downloaded pieces

A misclick writes files without completing their pieces, so the common case is the simple one. A file skipped after part of it arrived is different: libtorrent's record still says it has those pieces after the file is gone. Wanting the file again would then show it complete and download nothing (every kind of torrent, #115's second trap). A recheck clears that record, and a recheck is exactly what breaks on hybrid torrents. So the sheet treats those files by kind:

skipped filev1-only or v2-only torrenthybrid (v1+v2) torrent
No downloaded piece (the misclick)Stop, delete, start. No recheckThe same
Some downloaded piecesIncluded: stop, delete, start, then a recheck (safe on these torrents), named in the sheet before it runsLeft on disk, and the sheet says why. "Add the torrent again" frees them: remove it keeping files, add it back with the same selection, then reapply its category, tags and limits. It costs the torrent's ratio, seeding time and added date, and the sheet says so

Everything there comes from the API. A torrent is hybrid when torrents/info gives both infohash_v1 and infohash_v2. Which files hold downloaded pieces: torrents/files gives each file's progress and piece_range, and torrents/pieceStates says which pieces are downloaded (2). A file holds none when no piece in its range is downloaded; progress 0 is the quick check. A piece shared with a wanted neighbour counts as downloaded, so such a file is treated as holding pieces: on a hybrid it stays. That costs a little space, never a broken torrent.

Already in that error. A hybrid torrent that hit the bug only says error, with no text in qBittorrent's log or API; starting it or restarting qBittorrent brings the error back. omaseed's error block (board 28) can name it when an errored torrent is hybrid and was just rechecked, and offer the same "add it again". That is a small addition to board 28's causes, decided with D3.

Who can see the disk: a NAS too, when its share is mounted

The add sheet's free space (board 25 §4, FreeSpaceProbe) already decides whether omaseed can see the server's disks: the default save path, through the path map, has to exist on this machine and read within 1 % of the free space qBittorrent reports. That rule decides here too.

In the real case only 4 pieces had arrived, so the hint would have named a handful of files while 174 held 85.8 GB. 3 · proposal 2 · both kinds of disk

A big selection waits three seconds, with an undo

The cost in §1 came from the three seconds the whole torrent was wanted. #116 narrowed it further: the tick itself creates every newly wanted file at full length, even on a stopped torrent, before a byte downloads. Stopping first doesn't protect anything; only not sending the tick does. If a big widening waits a moment before it is sent, a misclick undone within that time never reaches qBittorrent. The rows tick at once, as today. Only the request waits.

what waits
Only a change that adds files, and only when it adds more than the threshold (D6). Running or stopped alike: the files are created when the tick arrives, not when the torrent starts. Skipping is always sent at once (it never costs space).
several changes
Changes made while one waits join it, and the window starts again. What is finally sent is the net change per file. If it nets out to nothing, nothing is sent.
leaving
Switching torrent, closing the pane or quitting sends what was waiting. You asked for it, so it isn't dropped silently.
the add sheet
Not affected: it adds the torrent stopped and sends the choices before starting, so nothing is written while you pick.
Rules against N1 as built. N1 says the Files tab does what qBittorrent's Web UI allows, and the code reads it as "the rows change at once and the request goes at once" (App::setFilePriority). This keeps the rows but delays the request for big widenings. It needs your ruling (D5); it would be recorded as a change to N1.
4 · proposal 3 · ntfs3, exfat, vfat

Name the disk's driver where it changes what a tick costs

The call omaseed already makes for free space (QStorageInfo) also reports the filesystem, and it names the driver, not the format: ntfs3, ntfs, exfat, vfat, ext4, btrfs. That matters, because the two NTFS drivers behave differently. #116 measured each with the same steps (Open Movie Night, 751 MB; only README and subs wanted):

fileSystemType()skipped from the starteverything ticked 3 s on a stopped torrent, then skippedkept after skipping
ntfs3 (with or without prealloc)0.3 MB750.8 MByes, full size
exfat0.4 MB750.8 MByes
vfat (FAT32)0.3 MB750.8 MByes
ntfs (the newer in-kernel driver)0.3 MB0, sparse~nothing
ext4, btrfs0.3 MB0, sparse~nothing
fuseblk (ntfs-3g), xfs, CIFS, NFSnot measured: tools not installed, no server at hand

So the notice is for ntfs3, exfat and vfat only, and it says the driver's name, not "NTFS": a disk mounted with the newer ntfs driver needs nothing. On those three, Save to in the add sheet and the destination in the Move sheet (board 43) say so, and the room check counts what the disk will really use: the full size of every newly ticked file, at the moment of the tick, not what is left to download. The same check runs on a tick in the Files tab, beside D5's window. On a spinning disk the notice matters twice: the space goes at once, and the first write near each file's end makes the drive write zeros up to it (§1).

Both errors come early, which is why the check belongs at the tick. FAT32 rejects a file of 4 GiB or more within 3 s of wanting it (file_truncate … File too large). exFAT, and by the same rule ntfs3, errors at once when a newly wanted file is bigger than the free space (file_truncate … No space left on device). fuseblk (ntfs-3g) and xfs get no line until measured; a server whose disks omaseed can't see gets none either: the API doesn't report a filesystem, and omaseed won't guess.

5 · proposal 4 · dropped (D10, ruled 2026-10-21) · and a small notice in its place (D13)

No incomplete-folder hint. A notice when a move never arrived

The idea was a hint in the qBittorrent settings pane: keep running downloads in a folder on a Linux disk and let qBittorrent move them to the NTFS save path when they finish. Dropped: an incomplete folder doubles the space a torrent uses while it downloads and adds a move step to every finish. Proposals 1–3 deal with the cost where it arises instead.

#117 measured it before the ruling. The fear of a file open at the finish doesn't hold on Linux: a 503 MB file held open from 2 % moved fine, and the reader kept reading the old copy (its space comes back when the reader closes). The real risk was a full destination, which is what D13 below is about.

D13 · finished, but still in the incomplete folder

Some people already use an incomplete folder. When the destination is full at the finish, the move fails silently. #117, a 38.9 MB torrent finishing into a disk with 22 MB free:

  • qBittorrent logs Failed to move torrent … file_write (<the source path>): No space left on device. The reason names the source file, not the destination that is full.
  • 699 partial files are left in the destination, which is now 100 % full. Nothing cleans them up.
  • The torrent stays stalledUP at 100 %, seeding from the incomplete folder. No error state, no retry, and a recheck changes nothing. save_path already says the destination; only content_path, still under download_path, shows the files never arrived.
when it shows
A finished torrent (progress 1), not moving, with a download_path set and its content_path under it. All three come from torrents/info, so it works on any server, seen disks or not.
the reason
The newest "Failed to move torrent" line for that torrent in qBittorrent's log, read through board 32's log feed. Without one, the notice says the files are still in the incomplete folder and doesn't guess why.
who sees it
Only people whose qBittorrent uses an incomplete folder. omaseed never suggests one (D10).
6 · proposal 5 · words

"Isn't answering" is not "unreachable"

At 12:13:55 qBittorrent was alive but waiting on its disk. omaseed's client already tells a timeout (ApiError::Kind::Timeout) from a refused connection (Network), but both end in the same words: "home · unreachable", and "server lost" in the log. The two need different words, because the advice differs: wait, or check that it's running.

The "busy writing to its disk" clause could be measured rather than guessed when the save disk is on this machine: the disk's own activity counters (/proc/diskstats) show whether it is saturated. That only works for qBittorrent on this machine or in Docker here, not over a network share, so it is a separate call (D12).

Desktop notice, rail line and command palette follow the same split ("home isn't answering" / "home is unreachable"). The notice titled "Server lost and back" becomes "home answered again" after a timeout.

7 · how it's built

Mostly pieces that exist, read from one more angle

FreeSpace
StorageReading gains the filesystem (QStorageInfo::fileSystemType(), as #116 read it: ntfs3, ntfs, exfat, vfat, ext4, btrfs). A small table says which allocate in full (ntfs3, exfat, vfat); unknown types (fuseblk, xfs, network mounts) get no notice. FreeSpaceProbe::Answer carries it to the add sheet, the Move sheet and the Files tab's tick check. Tests with a fake reader for each type.
SkippedOnDisk (new, core)
Given a torrent's file list (paths, priorities, progress, piece_range), its piece states and the local folder from FreeSpaceProbe::localPathFor, reads each skipped file's allocated size (st_blocks, not the length) on the thread pool and marks the ones that hold a downloaded piece. Refreshed when the Files tab opens and after a priority change, never polled. QtTest with a fake filesystem.
free the space
App::freeSkippedSpace(hash): stop, then delete through the path map, re-checking at delete time that each file is still skipped, inside the content path, not shared (board 26's guard), and not held open (/proc/*/fd on this machine); then start. Files holding downloaded pieces: included with a recheck after the start on a v1-only or v2-only torrent, left on a hybrid (infohash_v1 and infohash_v2 both set). Never a recheck on a hybrid. Each step goes to the problem log (C2).
add it again
For a hybrid's leftover files, and for a hybrid already in libtorrent's error: remove keeping files, add the same .torrent (torrents/export) stopped with the same file priorities and save path, reapply category, tags and limits, start. The sheet names what is lost (ratio, seeding time, added date) before it runs.
stuck move (D13)
A problem kind beside board 28's: finished, not moving, content_path under download_path. The reason is matched from the log feed (board 32) by the torrent's name.
the send window
A small queue in front of App::setFilePriority: widening changes above the threshold wait, running or stopped, merge per file, and are cancelled by undo. setLocalPriority still changes the rows at once. tst for merge, cancel, net-zero and leave.
words
The server line, the rail, the palette and the notices read the error kind they already get, and say "isn't answering" for a timeout.
walks
actions-walk gains a misclick and a free the space on a loop-mounted ntfs3 image, a hybrid and a v1-only torrent, checked on the server and on the disk. The mount is #116's: udisksctl loop-setup and udisksctl mount, no root. A stuck move is staged with a full loop image, as in #117.
engines
Nothing qBittorrent-only: Transmission's files-unwanted works the same way, and the disk side is omaseed's own.
