Engines in the window, v2

One window, three engines, and each says what it can't do in plain words. C14 settled how omaseed drives Transmission and Deluge besides qBittorrent; board 37 drew where the window learns and names a server's engine, but in v2's frame and before v0.3. This board redraws that ground inside board 46's frame and adds what v0.3 brought since: moves and the Move sheet, the error block, the add sheet's bare hash, settings scope, the seed console. Every "not on this engine" comes from the engine matrix (a working paper, §4, 22 October); nothing is guessed, and the three things it couldn't settle from the source are drawn both ways in §3.

§1 lists each feature per engine. §2 is the window, live, in both skins, with an engine switch: the same library on public (qBittorrent 5.3.0), seedbox (Transmission 4.1.3) and nas (Deluge 2.2.0 through deluge-web), so each surface can be compared. The calls are K1–K34 in §7; they carry 37's W1–W16 where still valid and say which each replaces. Nothing in E3's window is built before you rule.

3 · to verify on the E11 playgrounds

Three things the source suggests but nobody has seen

Each is checked before the step that relies on it. The design is ready for either answer, so the ruling doesn't wait for the check.

E · K22 · Transmission on :8085
Is Transmission's RPC busy during a long move?

A move runs in Transmission's session thread, and its RPC server shares that thread's event loop. Read from the 4.1.3 source, a long move across drives holds every answer until the move ends. To check: move a 2 GB torrent across drives and ask for the session every second.

if it holds
The band reads "seedbox is busy moving NAME · it answers again once this torrent has moved"; the list is marked stale; timeouts while a move to it is in flight count as moving, not as C12's "didn't answer", until M14's stuck threshold; then C12 as today.
if it answers
Nothing new: the ordinary band, and C12's notice only if Transmission really stops answering.
E · K23 · Transmission on :8085
Does Transmission's move replace a file already at the destination?

It moves file by file with tr_file_move, which on the same drive is rename(2), and rename replaces the target. What a copy across drives does is unknown. To check: a different file by the same name at the destination, on the same drive and across drives.

if it replaces
The Move sheet's M8 line reads "Transmission would replace that file with this torrent's: it stays behind", and the job leaves that torrent out, as it does on qBittorrent. On a Transmission whose disks omaseed can't see, the names line adds "a file already there may be replaced".
if it keeps it
The line reads as qBittorrent's and Deluge's ("would keep that one and call the move done: it stays behind"), and the remote line drops "may be replaced".
G · K26 · deluge-web on :8086
Does Deluge's metadata prefetch work through deluge-web?

core.prefetch_magnet_metadata is one blocking call (30 s by default) that answers with the hash and the metadata, or empty on a timeout. deluge-web passes core methods through /json, but a long call through it hasn't been tried. To check: a magnet with a live swarm, called again after each timeout, while the list keeps polling.

if it works
C5's waits and words as on qBittorrent (fetching, still looking, may never come), driven by repeated calls; a short timeout per call if a long one holds deluge-web's other answers.
if it doesn't
Transmission's sheet: one dim line, and the files are picked in details after the add.

Checked at the same time, for K10: whether connecting deluge-web to a daemon changes it for deluge-web's other users. If it does, the daemon step says so once before it connects.

4 · what stays out of sight

Handled at the engine's edge, with nothing to draw

  • Sync: qBittorrent's incremental maindata; Transmission's recently active list and Deluge's full list through a shared differ. Version probing, Transmission's 409 and session id, its integer ids mapped to hashes.
  • Units: B/s, Transmission's kB/s (1000 bytes) and Deluge's KiB/s. Tracker lists and Transmission's labels replaced whole (read, change, write). Labels and limits set right after an add when the engine takes none at add.
  • Start, stop, recheck, reannounce, queue, delete, file renames: one verb each, mapped per engine. Peer lists, magnet links, free space by path (it only removes L13's "room can't run here").
  • Failed moves (the TODO in QbtMoveFeed.hpp): QbtMoveFeed becomes MoveFeed, with one failure source per engine. qBittorrent's is the log, as today. Transmission's and Deluge's are the torrent going into error after its send while its folder is still the old one, the engine's text kept for the block and read by ErrorWords for the cause. They feed MoveJob the same failure it takes today, so only the words and the retry verb show (F). Deluge's event queue can bring it within one poll.
  • Transmission's NAME.part files in board 44's disk scan; Deluge's per-session event queue as a quicker path to the same signals.
