Search, through qBittorrent's search plugins

omaseed never names, ships or scrapes a site. Search goes through qBittorrent's own search API, with the plugins the user chose and installed on their server. What omaseed adds is how the answers read: rows that fill in as each plugin answers and never block the window, one row per torrent however many plugins found it, seeds that say how healthy it is, "unknown" kept apart from "dead", a plugin that failed named instead of hidden, and, seed first, a mark on what is already in your library or on your disk. Adding goes through today's add sheet, so categories, the save path, the file picks and the library match work as they do now.

§1 is what qBittorrent's API gives and doesn't, probed on the playground. §3 is the window, live, in both skins, in board 46's frame (its H16: search is a rail view after log, ctrl+f, results in the rows display). The calls are SR1–SR14 in §9, each with a recommendation. Nothing is built before you rule.

1 · what qBittorrent gives

The search API, as qBittorrent 5.3 answers it

The playground (qBittorrent 5.3.0, Web API 2.16.2), probed with four invented local plugins that print fixed rows and touch no network: one quick, one that raises, one that reports no seed counts, one that sleeps 25 s. Removed afterwards, jobs deleted. Read beside qBittorrent's WebAPI_Changelog.md and its search sources.

endpointwhat it doeswhat we saw, and what it means for omaseed
search/startpattern, category (all or a type), plugins (enabled, all, or names joined by |) → {id}Starts at once and runs on the server. 409 "Python must be installed" when the server's machine has no Python. 409 at five running searches, server-wide: the Web UI and any other client share them. With no plugin it still makes a job, which stops with nothing.
search/statusevery job, or one: status Running or Stopped, total, and since 2.16.1 pattern, category, pluginsNo state per plugin. A job of four plugins ran until the slowest ended (25 s), and qBittorrent ends any job at 3 minutes. Stopped is the same word for done, failed and cancelled.
search/resultsid, limit, offset → results, status, totalEach result: fileName, fileSize (bytes), fileUrl (a magnet or a link to a .torrent), descrLink, nbSeeders, nbLeechers, pubDate, siteUrl, engineName (2.17 adds engineFullName). −1 means not reported, for seeds, leechers and the date. engineName is found by the plugin's site URL, so two plugins sharing one URL come back under one name. Pages with offset: omaseed asks only for what is new.
a plugin that fails—Nothing in the API: the job carries on and ends Stopped like any other. qBittorrent's log gets a warning, "Error occurred in search engine… Engines: …", with the traceback, which names the plugin's file. omaseed already reads that log (C2, C3). A plugin that lacks the chosen type is skipped without a word.
search/stop, search/deleteend a job; forget itJobs stay on the server until deleted, and with 5.3's store_search_jobs they survive a restart, in every client's list (SR12).
search/pluginsthe installed pluginsname, fullName, version, url, enabled, supportedCategories ([{id, name}]: the types a plugin knows).
search/installPluginsources: URLs or paths, joined by |Answers 200 at once, whatever happens. A missing file or a non-.py file left no trace, not even in the log; a good one appeared in the list within a second. A path is read by the server, on its own machine, so a file on this computer reaches only a server on this computer (SR10).
search/uninstallPlugin, enablePluginnames; enableBoth quick and quiet; the list shows the change.
search/updatePluginscheck for updatesqBittorrent checks its own project's plugin list and updates plugins that are on it. The answer is in its log only ("All plugins are already up to date", "Plugin … is outdated, updating to version …", "Failed to check for plugin updates…"). A plugin from anywhere else never updates this way.
torrents/add, fetchMetadatadownloader (2.13.1)A result's link to a .torrent can be fetched through its plugin, which knows what the site needs. So the add sheet takes a link from search the way it takes any link (C5 D8), with the plugin's name.

Transmission and Deluge have no search (engine matrix §4.10): on such a server the view isn't offered (board 47's rule: gone where it would be offered, said on its key). §7, and .

4 · a result, as a row

It reads like a torrent: the name, one sentence, one fact

Board 46's rows display (law 3: words first), with a result's own parts. Nothing from a plugin is shown that the plugin didn't send.

left
Health, as the glyph's colour

Green with five seeds or more, yellow with one to four, dim when not reported or none. A result already in your library takes its torrent's state (↓ arriving). A link to a .torrent shows ⋯.

line 1
Name · size · age · a mark

The name as the plugin gives it (the most-seeded copy's), the size it says, its age from pubDate ("no date" when −1). Then one mark at most: in your library, likely on disk, added; and while it fills in, new or +1 copy.

line 2
Who found it, and what to know

The plugins that found it, the copies folded and the trackers in the magnet, the leechers; or the one thing that matters instead ("this plugin doesn't report seeds: unknown, not dead", "a .torrent link: its info hash is known at add"). Then add…, or trackers… on a torrent you have, shown on the cursor row and under the pointer only.

right
The fact: seeds

"41 · seeds", "3 · few seeds" in yellow, "? · not reported", "0 · no seeds". The leechers stay on line 2 and in the result's facts. When the seeding coach comes back (#25) its words for a swarm go here (SR8).

5 · plugins, and the line omaseed holds

The user's plugins, on their server; omaseed only carries the answers

omaseed shows
  • The plugin's own name (fullName), version and types, from the user's own server: their data, not omaseed's words.
  • What each plugin answered in this search, and when one failed, its line from qBittorrent's log.
  • A result's page (descrLink) only when asked: open its page (o) opens it in the browser.
  • An install field that takes a URL or, for a server on this computer, a file.
omaseed never
  • Names, suggests, ships, ranks or links to a plugin or a site, nor to a page that lists them (qBittorrent's wiki included).
  • Fetches a site itself: every request to a site is qBittorrent's, through the plugin (search, and a .torrent link through downloader).
  • Shows siteUrl's host in a row, or opens descrLink without a click.
  • Keeps results after it quits, or searches on its own.

7 · servers, and engines without search

Search belongs to the server you are on

two servers ·
The current one only

The title's sentence ends "on public". Plugins differ per server, and an add goes to one server, so a search never runs on two. Switching servers shows that server's own search, or its empty state; each server's last results are kept until omaseed quits (SR12).

a server in trouble ·
Search waits for it

C12's notice under the title; the rows dim as a stale list does; the sentence says "public isn't answering · search waits for it"; enter asks again when it is back.

Transmission, Deluge ·
No search there

Neither has search plugins. On such a server the rail has no search row; ctrl+f and : "search…" say "private (Transmission) has no search" in the status line (board 47's W16). Nothing offers to search another server instead.

a remote qBittorrent ·
URLs only

Search works the same on a remote server. Installing a plugin from a file doesn't: qBittorrent reads the path on its own machine. The pane says so and takes a URL.
