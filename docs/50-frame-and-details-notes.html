2 · #167 · the outcome strip's "show"

Show only what isn't already in front of you

C18 gave every done strip a "show" (the cursor on the one torrent, or the several selected; a move that took them out of the rail's folder switches the folder). Acting from a selection, the torrents are almost always already selected and on screen, so "show" is a button that does nothing. The ruling: hide it then, keep it when one scrolled away or left the scope. Below in board 46's frame, the status line as the action bar (H8), the strip floating just above it.

How "on screen" is read. The strip knows its torrents (C18's outcome record). "show" stays hidden while each of them is in the current scope (folder, question, category, tag, the filter text), inside the visible part of the list, and selected (or, for one torrent acted on alone, the cursor's row). Any one failing brings "show" back, with the reason as its dim line (F10). Stopping from "giving back" is the common case of leaving the scope: they are resting now, and "show" takes the rail to resting.

A hybrid whose skipped files were downloaded before they were skipped: the band offers "Free the space…", shift+f and the palette do too, and the sheet then says there is nothing to free, with a disabled "nothing to free" as its main button and the way out as a line of text. So the band, the palette row and shift+f decide from what the Files tab already read; nothing new is asked. The edge case is a file at progress 0 whose first or last piece it shares with a downloaded neighbour. Hybrid and v2 torrents align every file to a piece (pad files), so there it should not happen; on v1 the plan deletes such a file anyway, with its recheck. When shift+f comes from the table before the Files tab has read anything, omaseed reads it then (the same two calls) and goes to the confirm or the sheet. If the plan at delete time (which reads pieceStates again) finds nothing to free after all, the sheet opens in its "nothing to free" form with the re-add as its main button.

4 · #169 · the size that doesn't shrink

A skipped file still on disk still counts

qBittorrent's size counts the pieces it has, and a file skipped after it was downloaded keeps its pieces, so the torrent's size stays where it was (checked on v1, hybrid and v2: the walk's v1 torrent reads 32.0 MB with 16.0 MB skipped and on disk, and drops to 16.0 MB only after the space is freed and rechecked).
