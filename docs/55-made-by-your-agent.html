omaseed · board 55 · 2026-11-05 · a proposal · #221

Made by your agent

herdr's desktop app can be reshaped by the person's own coding agent. Ask it for "a sidebar of my PRs" or "make it warmer" and the agent edits files the app redraws itself from. omaseed already has half of that: since C31 a skin is data, a versioned skin.json read all or nothing at the file, its colours always theme roles. This board proposes the other half, for skins only: skins in the person's own folder, a guide written for the agent beside them, and a way for the agent to check its work without a display. omabox is the better way to look when it is installed, never a requirement. Panels that add features, faces written as code and other view layouts stay off this board.

1 · how herdr does it

The interface is files, and the manual sits beside them

Read from herdrdev/herdr-app, its defaults/AGENTS.md and docs/security.md.

  • Files the window redraws from. layouts/<name>.json (a tree of blocks with its look), keys.json, themes/*.json, and mods/<name>/main.js: small JavaScript programs that describe native GPU elements, drawn by Rust. No HTML, no web view. A save reloads within a second.
  • Its own panels are mods too. The sidebar, the agents list, the tab bar, menus, dialogs, toasts, Settings and Welcome are built from the same API a person gets, so the API is whole by construction.
  • The manual is the agent's, and it is where the files are. On every start the app writes AGENTS.md (about 1,000 lines) and its type files into ~/.config/herdr-app/, matched to the installed version. An agent started there reads it without being told.
  • The agent checks its own work. herdr-app check <mod> loads and renders once and exits nonzero with the error; a bad save keeps the last good version and writes <name>.error; herdr-app shot saves the window as a PNG; herdr-app do runs any command. One key always goes back to the default layout, and nothing can rebind it.
  • Clone, don't edit. Shipped layouts and mods are replaced on every start; a person duplicates one first. A shipped file edited anyway is moved aside as <name>-edited.
  • Shared as a recipe. A shared mod carries a RECIPE.md: the brief another agent builds it from in an empty folder. The files are one build of it.
  • Trusted code, said plainly. A mod can run programs, fetch URLs and read files, with no prompt.
What carries over to omaseed now: the person's folder, the guide beside it, a check that needs no display, clone before you change. What waits: code from the person's folder. QML runs JavaScript, and omaseed's actions can delete a library with its files.
2 · today, in an omabox

Two skins, both built in

  • What a skin holds (C31): roles, grounds, line, cut, tint, radius, font, label, select, plates, meter, numerals, density, glyphs, labels, glow and faces. Colours are a role and an alpha over a ground, never a hex, and C30's floor keeps every text at 4.5:1 on whatever ground the skin sets.
  • All or nothing at the file. A file that doesn't parse, has no integer version, is newer than omaseed or names an unknown skin is drawn whole as Omarchy's, with the reason logged. Inside a file that reads, each malformed token falls back alone and is named in dropped.
  • Faces are code. faces maps the four seams (Plate, SelectionMark, Meter, Lamp) to whole QML files in the skin's faces/. Both skins live in src/ui/skins/, compiled into the binary.
  • C31 already planned this: "User skins later: from ~/.config/omaseed/skins/<name>/skin.json, listed in Appearance, under the same version rule. The first user-skin version is data only; faces from a user folder are code and need their own ruling."
3 · the whole loop, with every option recommended

"Make omaseed warmer, and rounder"

you     make omaseed warmer, and rounder

agent   reads ~/.config/omaseed/AGENTS.md            written by omaseed on every start (U4)
        omaseed skin clone omarchy warm              → ~/.config/omaseed/skins/warm/skin.json (U3)
        edits skin.json: roles, grounds, radius     role names and alphas, never a hex
        omaseed check warm                          → what it read, what it dropped, a PNG (U5)
        … fixes what check named, checks again
        omabox: the shipped check script            every Omarchy theme, a baseline (U7; if installed)
        omaseed skin use warm                       → the open window repaints, live (U6)

you     look at it in place. "less orange" → another round

The agent never sees the person's library: check draws invented torrents in the person's own theme, base size and fonts, and skin use changes the window the person is looking at. Every step works without omabox; with it, the check covers every theme and says what moved.

4 · U1 to U3 · the person's folder

Skins beside the built-in ones

U1 aRead from the person's folder, listed in the Skin row, liverecommended

omaseed reads every skins/<name>/skin.json under $XDG_CONFIG_HOME/omaseed/ (~/.config/omaseed/) with the same reader and the same version rule as the built-ins. A user skin's name is its folder; a folder named like a built-in (omarchy, console) is ignored, with the reason logged. The Skin row lists them after the built-ins, with open folder beside them. omaseed watches the folder: saving the skin that is drawn repaints the window, as a theme change does today. A save that breaks the file draws Omarchy's skin and names the reason in the row; the next good save draws it again.

mockSettings › Appearance › Skin
◑SkinWarmer and rounder. OmarchyConsolefollow the desktop yourswarmpaperopen folder warm: 1 token left at Omarchy's: grounds.hover.alpha 1.4 isn't between 0 and 1.
  • The caption is the skin's own description (a new optional field), else its folder.
  • More than three of the person's skins: the second line becomes one chip, yours ▾, opening the palette Settings uses for lists. open folder opens skins/ in the file manager.
  • The yellow line shows only while the drawn skin has dropped something, or was dropped whole (then: warm isn't drawn: version 2 is newer than this omaseed).

U1 bRead once, at start

No watching: a change shows on the next start, or through omaseed skin use. Simpler, and slow for an agent working round after round.

U2 aData only: a user skin may name a built-in skin's faces, never a filerecommended

Answers the question C31 left open. In a user skin, faces picks each seam from a built-in skin: "faces": { "Plate": "console", "Meter": "omarchy" }. A path, or a faces/ folder beside the file, is dropped and named. So "Console's panels with Omarchy's quiet meter, in my colours" is a skin, and no code from the person's folder ever runs. Faces as code wait for the mods board (§8).

U2 bFaces from the person's folder too

A user skin's faces/*.qml loads like a built-in's. Full freedom for the four seams, and JavaScript from a folder any agent writes into, drawn inside the window that holds the server's session.

U2 cFaces as code, behind a switch

As b, only after Settings › Appearance, Run code from my skins, is turned on. The switch says what a face can do; most people never see a reason to flip it.

U3 aStart from a copy: omaseed skin clonerecommended

omaseed skin clone <from> <name> writes a whole skin.json into skins/<name>/: every token written out (Omarchy's included, which has none in its own file), with "cloned_from": {"skin", "version"}. <from> is a built-in or one of the person's. An existing name is refused. The copy is the person's and never changes when omaseed's skins do; herdr does the same.

U3 bInherit: "base": "console"

A user skin names a built-in and overrides a few tokens, so it follows omaseed's changes to that skin. Shorter files, and a look that can shift under the person after an update without their agent having touched it.

5 · U4 · the guide

Written for the agent, where the agent will be

U4 aAGENTS.md and a schema in ~/.config/omaseed/, rewritten on every startrecommended

omaseed writes, when they differ from what it would write:

  • AGENTS.md, headed Written by omaseed on every start. Edits here are overwritten. Codex, OpenCode, Cursor and the rest read it.
  • CLAUDE.md, one line, @AGENTS.md, because Claude Code reads only that name. Either file is left alone if it exists and isn't omaseed's (no header).
  • skin.schema.json: every token, its type, range and default, generated from the reader's own table, so the guide can't drift from the version that wrote it. omaseed skin clone points $schema at it.

omaseed --skill prints the same guide, for an agent started anywhere else. It covers: what a skin is and isn't; which files are omaseed's (state.json, servers.json, moves/: never edit) and that no credential is ever in this folder; the token reference; the rules (roles and alphas, never a hex; C30's floor; sizes from base size); the commands; the omabox section (U7); the way back (U8); sharing (U9). It is short: one skin, one file.

U4 bOnly omaseed --skill

Nothing written into the person's folder; an agent finds the guide only if told to run it. The folder stays tidier, and the agent starts each session not knowing the folder is meant to be edited.

6 · U5 and U6 · how the agent knows it worked

A check that needs no display, and no library

U5 aomaseed check <skin>: what it read, and a picturerecommended

No window, no D-Bus, no server: Qt's offscreen platform. It reads the skin with the app's reader and the person's current theme, base size and fonts, then draws one fixed sheet: the demo library as rows and as a table, a menu, a sheet, a notice and the four seams in each state, light and dark grounds as the theme gives them. It prints what an agent needs to fix:

$ omaseed check warm --json
{
  "skin": "warm", "version": 1, "drawn": true,
  "dropped": [ { "token": "grounds.hover.alpha", "value": 1.4, "why": "not between 0 and 1" } ],
  "missingFonts": [],
  "lifted": [ { "role": "dim", "ground": "picked", "from": 3.1, "to": 4.5 } ],
  "theme": "tokyo-night", "baseSize": 14,
  "picture": "/home/you/.cache/omaseed/check/warm.png"
}
  • Exit 0 when the skin is drawn (tokens dropped one by one are listed); 1 when the file is drawn whole as Omarchy's, with why; 2 for a usage error. Without --json, the same as lines.
  • lifted lists what C30's floor had to lift: readable anyway, but a hint that a ground is louder than the agent meant.
  • --theme NAME draws under another installed Omarchy theme instead of the current one.

U5 bA lint, with no picture

The JSON without the drawing. Cheaper to build, and the agent is left guessing how it looks, or asking the person to describe it.

U6 aThe open window: omaseed skin use, and no shot of itrecommended

omaseed skin use <name> asks the running omaseed, over its D-Bus name, to draw that skin and save it as the choice (without one running, it saves the choice for the next start). omaseed skin list [--json] names every skin, where it lives and whether it reads. There is no command to capture the open window: it shows the person's library, torrent and folder names, and a picture sent to an agent goes to its model's provider. check's picture shows the same skin in the same theme on invented torrents.

U6 bAlso omaseed shot

As a, plus omaseed shot [file.png]: the running instance saves its window as a PNG, even when covered, as herdr's does. The agent sees the real thing, real library included; the guide would tell it to ask the person first.

7 · U7 to U10

omabox, the way back, sharing, and the commands

U7 aomabox as the better way to look, never a requirementrecommended

  • The PKGBUILD lists omabox in optdepends (check a skin in every theme, in a desktop of its own).
  • omaseed ships /usr/share/omaseed/agents/skin-check.sh, a script for omabox check run: a box, omaseed --demo drawing the skin, a pass for each Omarchy theme (the light ones too), a window shot each and omabox tree's controls; the first run makes a baseline, later runs say same or what moved. The guide's omabox section is that command and how to read its report.
  • No qBittorrent in the box: a skin needs only the demo library. A throwaway server comes with the mods board, where an agent's panel can act on torrents.
  • Without omabox, check ends with one line: omabox would check this skin in every theme, in a desktop nobody sees: omabox.app. Never more than that line, and nothing in omaseed waits for it.

U7 bMention it in the guide, ship no script

The agent learns omabox exists and writes its own check each time.

U7 cLeave omabox out

check's picture is the only look.

U8 aThe way back: no new keyrecommended

A skin can't hide text (C30's floor) or break the window (the reader falls back), so the risk is a skin the person dislikes. omaseed skin use omarchy, the Skin row, and OMASEED_SKIN=omarchy omaseed for one run always work; the guide names all three, and clone never touches the skin it copies.

U8 bA fixed key back to Omarchy's skin

ctrl+alt+shift+esc, unbindable, as herdr's. Worth it if U2 b or c lets code in; with data only it guards against little.

U9 aSharing: a folder, a recipe, a topic; no gallery yetrecommended

A shared skin is its folder in a public repo with skin.json, a RECIPE.md (what the person sees, the tokens it sets and why, what to check) and a preview.png from check, tagged omaseed-skin. The guide says how to share one, and how to add one: read every file first, copy it into skins/, never overwrite (rename on a clash), check it, skin use it. A gallery on the site waits until there are skins to show.

U9 bNothing about sharing yet

The guide covers one person's skins only.

U10 aWords after omaseed, the family #163 will growrecommended

omaseed check, omaseed skin clone|list|use, omaseed --skill; #163's status, errors, log and moves join them later, behind the same D-Bus name. A first argument that is one of these words is a command; a file named like one is opened as ./check, as with any program. One way in for agents, not two.

U10 bOptions: --check, --skin-clone

Beside today's --demo and --quit: no clash with file names, and a longer help page.

8 · not on this board

Later, each with a board of its own

  • Panels that add features (herdr's mods): QML from the person's folder in a slot (the rail, a dock, a sheet), against a small public Omaseed module (torrents(), servers(), theme(), run(action, args)), actions only and never the client or a credential, destructive ones through omaseed's confirm, tested against a box's throwaway qBittorrent. Worth a frozen API only once people make skins.
  • Faces as code, if U2 a: with the mods, under the same rules.
  • Other arrangements of a view: a skin must not fork View layout (C31; #199).
  • A skill installed into Omarchy's skills folder: that folder is Omarchy's, not a package's. omaseed --skill and the written guide cover it.

10 · building the recommended options

Six pieces, after the add window (#218 to #220)

  1. The folder. SkinReader lists and reads skins/*/skin.json under the config home, takes description and cloned_from, refuses built-in names, and resolves faces to built-in faces only (a path is dropped). A QFileSystemWatcher on the drawn skin's file and on skins/. The Skin row's second line, yours ▾ past three, open folder, the yellow line. QtTest for the reader's new cases.
  2. The commands. Words before Qt's parser in main.cpp: skin clone and skin list with no display; skin use through the running instance's D-Bus object (a new method), else state.json. Exit codes as U5.
  3. The check. omaseed check on the offscreen platform: the reader's verdict, the floor's lifts (from ThemeInk), and the fixed sheet drawn from the demo library to a PNG under ~/.cache/omaseed/check/. Its QML is a View of its own, in both skins' ctest runs.
  4. The guide. AGENTS.md, CLAUDE.md and skin.schema.json written at start when they differ; the schema from the reader's table; omaseed --skill. A ctest that the schema names every token the reader knows.
  5. omabox. data/agents/skin-check.sh installed to /usr/share/omaseed/agents/, optdepends in the PKGBUILD, check's one line when omabox isn't on PATH. shellcheck-clean.
  6. The proof. scripts/dev/skins-walk.sh: in a box, clone, break a token, check (exit 0, dropped named), break the file (exit 1), fix it, skin use with the app open (it repaints), the Skin row's lines. Then the real test, once released: an agent in a fresh box asked for a skin with only the written guide, and what it trips on goes into the guide. README's "Make it yours", the ruling in docs/DECISIONS.md, released alone (C33).
