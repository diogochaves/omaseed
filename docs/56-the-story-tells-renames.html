omaseed · board 56 · 2026-11-06 · a proposal · #236

The story tells renames

The details pane's what happened is meant to be the torrent's story: when it came, where it went, when it finished, what went wrong. Rename a torrent, though, and the story doesn't notice. Press r, give it a better name, and the pane still reads only Added, on every engine. The old name is gone from the window, and nothing says it was ever there. This board proposes the rename line: its words and time, file renames as well as the torrent's name, renames made outside omaseed, several in a row, what each engine's rename actually changes, and where the record lives. Other quiet edits the story also misses (a category, a location set elsewhere) are named here and left for a board of their own.

1 · today, in an omabox

The story has four kinds of line, and none of them is a rename

  • What the story knows (core/TorrentStory, C24 H6): Added with its category, each Moved to PATH the move history keeps (C18 D8), Finished downloading, and the failure and the error at the times qBittorrent's log wrote them. Newest first (C32 D15). Its header comment sets the rule: only what omaseed knows for sure goes in.
  • Where a rename goes today. App::rename sends torrents/rename, and the outcome strip says NAME renamed for 6 s (C18). renameTorrentFile (r in files) and renameTorrentFiles (board 18's sheet) send renameFile / renameFolder per file. Once the strip is gone, nothing remembers any of it.
  • What a poll can see. The sync diff carries each torrent's name, so a torrent's name that changes between two polls shows, whoever changed it. File names aren't in the sync at all: omaseed reads a torrent's files only for the torrent open in the details. A file renamed elsewhere can't be seen happening.
  • What each engine's rename changes (board 47 §2 G, K28): on qBittorrent and Deluge (its name option) it changes the name shown, and the files on disk keep theirs. On Transmission, torrent_rename_path on the root renames the folder on disk as well, and the rename sheet already says so.
2 · R1 to R3 · the line

A rename, told like a move

engine renames in a row (R6)

R1The torrent's name: the wordsrecommended a

a: Renamed, its dim line was OLD. That's the issue's wording. The head right above already says the name now, so the line gives what you lost: the old name. Read newest first, a chain still adds up, since each line's was is the line below's name. b: Renamed to NEW, dim was OLD, as Moved to PATH reads. Both names, but for the newest rename it repeats the head, and two long names wrap to four lines. c: Renamed from OLD, nothing under it.

The time is when the server said OK, in the story's own time words (timeWords: 14:03, yesterday 21:10, 12 Oct 09:15). The screen reader hears it as the other lines (#79): 14:03, Renamed, was night.market.rec.2026.

R2The markrecommended a

a: the accent, as a move's. The accent then marks what was done to the torrent, and the neutral square (#201 F19) what the torrent did by itself (it was added, it finished); yellow and red stay the log's. In code that is a new kind, rename, painted as move. b: neutral, as Added: a rename changes nothing in where the data is or how it's doing, so it shouldn't catch the eye. c: a colour of its own. There's no Theme role free for it, and Q19 keeps the roles' meanings.

R3Files and folders inside the torrentrecommended a

Board 18's sheet renames many files in one run, and r in files renames one file or one folder. a: one line per run, said as the outcome strip counts it:

What was renamedLineDim line
the torrent (r on a row, the sheet's fallback)Renamedwas OLD (R1)
one file (r in files)Renamed a fileOLD → NEW, then in FOLDER/ when it isn't at the top
one folder (r on a folder in files)Renamed a folderOLD → NEW
several files, board 18's sheetRenamed 12 filesin FOLDER/ · the first OLD → NEW, and 11 more (in 3 folders when they span several)

b: the torrent's name only. The files tab shows the names now, and a run of file renames is rarely something you come back for. c: a line for each file. Twelve lines for one rename sheet push the rest of the story out of the pane.

Only omaseed's own file renames can be told: the sync has no file names (§1). A file rename that qBittorrent answers OK and then logs as failed (docs/32, C2 D2's 30 s watch) takes its line back. The failure line, yellow, tells it instead, so the story never claims a rename that didn't happen.

Recommended: R1 a, R2 a, R3 a. The rename reads like the move it sits beside: an act in the accent, the time it happened, one short dim line with what you'd otherwise have lost. One run is one line, however many files it touched.

3 · R4 and R5 · renames omaseed didn't make

Seen in a poll, made elsewhere

R4Renamed in another client, while omaseed runsrecommended a

qBittorrent's Web UI, another app, a script: the next poll shows a new name, and omaseed knows it didn't send that rename. a: the line, with the dim line saying who: Renamed · was OLD · renamed outside omaseed, the words C18 D7 uses for a move made elsewhere. Its time is the poll that saw it, 5 s late at most while the window is hidden. b: the same line with no difference. It's the same event, but then the story claims omaseed did something it didn't. c: only omaseed's own renames, so the story misses half of them, and #236 stays half open.

  • Not a rename: a magnet whose name fills in when its metadata arrives (the name was the link's dn or the hash). A change while the torrent had no metadata yet (no size) is never a line.
  • Its own echo: omaseed's own rename shows in the next poll too. A poll's new name that matches a rename omaseed sent for that torrent (pending, or answered in the last minute) is that rename, not a second line.
  • A file renamed outside can't be seen happening (§1), so it has no line. The files tab shows the new name.

R5Renamed while omaseed wasn't runningrecommended a

a: left out. omaseed sees changes only while it runs, and it runs in the tray all session (the poll goes on with the window hidden), so the gap is the time the server runs without it. Every other line's time is a moment, and this one's would be a span: the story's time column has no words for between Tuesday and today. b: omaseed keeps each torrent's name per server and compares on the first sync after it starts. The line then reads Renamed while omaseed was closed · was OLD, with the time it noticed. Every torrent's name gets stored for the one line, and the time isn't when it happened.

Recommended: R4 a, R5 a. The story tells what omaseed saw, at the time it saw it, and says when it wasn't omaseed's doing. It doesn't make up a time it can't know.

4 · R6 · several in a row

A typo fixed is one rename

R6Renames of the same thing, close togetherrecommended a

You rename, notice a typo, rename again a minute later. a: fold. Renames of the same name (the torrent's, or the same file or folder) within 10 minutes of each other, with no other line between them, are one line. It takes the last one's time and keeps the name from before the first (was night.market.rec.2026). A run that ends on the name it started with leaves no line at all. Use the switch over the mocks to see it. b: each its own line, always. Honest, but a typo fix costs a line of the story forever. c: keep only the latest rename of the torrent's name, so older names are lost even days apart.

The fold is done when the record is written, not when the story is drawn: the record keeps the run's first old name and its last time, and a rename back to the start removes it. Renames seen in a poll (R4) fold the same way, with each other but not with omaseed's own.

a: only Transmission's line adds a part, because only there did something on disk change. The rename sheet said so before (K28 a) and the story keeps it said. On qBittorrent and Deluge a rename is what people expect it to be, and saying the name only on every line is noise. b: every engine says what changed. c: no difference; then Transmission's line hides that a path the user's other tools point at has moved. On Transmission a rename seen in a poll (R4) changed the folder too, and says so the same way. File and folder renames (R3) change the disk on every engine, so their lines read the same everywhere.

6 · R8 and R9 · the add, and how long

Where the story starts, and what it keeps

R8Renames made in the add sheetrecommended a

The add sheet takes a name for the torrent, and M18 renames files in it, sent right after the add. a: no line. The story starts at Added, and a torrent added under a name was never called anything else in this library. b: Added's dim line grows: into music · as NEW, its own name OLD. The .torrent's own name, kept for whoever wants it, makes the first line long on every torrent named at the add.

R9Where the record lives, and for how longrecommended a

The server keeps no rename history, so the story's renames are omaseed's own record, per server, saved beside the move history in the server's state (C18). a: for as long as the torrent is in the library, the last 10 rename lines per torrent, dropped when the torrent leaves the server. A line is a handful of short strings, and a story that still says Added a year on but has forgotten last month's rename reads wrong. b: as moves, the last 20 or 30 days (C18 D8). One rule for both, but moves are capped because their records are large (every path, the loose files), and renames aren't.

7 · R10 · the other quiet edits

Named here, designed later

R10Category, tags, a location set elsewhererecommended a

Other edits leave no line either: a category or a label changed, tags added or taken away, a save path set outside omaseed (C18 D7 already knows such a move breaks move back, and the story doesn't tell it), a limit or a priority changed. Most of them would use the same record and the same poll as R4. a: a board of their own, later. An issue is opened when this board is ruled, naming the edits above. This board builds the record so it can take them, and draws none of them. b: add them here now. Each needs its own words and its own answer to is this a story or just a setting?, and #236 is a rename. c: never. The story stays a story of where and when, and settings stay in facts.

9 · building the recommended calls

Four pieces

  1. The record. core/RenameHistory, pure data like MoveHistory: one per server, saved through the same hooks, record() doing R6's fold as it writes, R9's cap, and prune(hashes) after a full sync. tst_renamehistory: the fold, a run that ends where it began, the cap, the prune, the JSON round trip.
  2. What writes it. App::rename's OK writes a torrent record (with disk set on Transmission, R7). renameTorrentFile's and renameTorrentFiles' answers write one record per run (R3). The sync engine reports a name that changed between two diffs for a torrent with metadata. If it isn't the echo of a rename omaseed sent (R4), it's a record by: elsewhere. The log watch that catches a failed rename (C2 D2) removes that run's record.
  3. The story. StoryInput.renames, the words of R1, R3 and R7 in TorrentStory::events, StoryEvent::Kind::Rename and kindName rename. DetailsStoryEvent.qml paints it as move. tst_torrentstory gets each row of §2's table and §5's.
  4. Walks. scripts/dev/actions-walk.sh already renames a torrent. It goes on to read the story's new line, rename twice in a row (one line), rename from the playground's API (renamed outside omaseed), and run board 18's sheet (Renamed N files). The engines branch's Transmission walk (#85) checks its folder on disk too.
