omaseed · board 57 · 2026-11-11 · a proposal · #88

A library moves between engines

omaseed speaks to qBittorrent, Transmission and Deluge, but a library can't yet go from one to another. Only a qBittorrent exports and imports its torrents (C9); board 36 left the rest as a later step, move a library (C14 E10), and K33 kept the other engines' settings groups without a Backup section. This board proposes that step: the same engine-neutral file, written by any of the three and read by any of the three, with the data left where it is on disk. Most of it is what each engine's API allows, measured on the playgrounds, and ten calls about what to do where two engines don't agree.

1 · today, in an omabox

One engine has the two rows; the others have nothing

  • The file is already neutral (core/TorrentsBackup, C9): a private tar with a manifest and, per torrent, a record (folders, category, tags, limits, renames, priorities, trackers, state) beside its .torrent, or its magnet link when it has no metadata yet.
  • The import is already careful: everything is added stopped, save paths go through the path-map rows, every torrent is checked, only complete ones start, a clash on disk stops a rename, and a run that is cut short resumes from its journal.
  • What is qBittorrent's is the code that reads and writes (engines/qbt/TorrentsExport, TorrentsImport) and the feature flag (torrentsBackup, off on the other two).

Two traps found on Deluge. Wanting a skipped file again on a complete torrent leaves it unremovable until the daemon restarts, so priorities go in the add, never after the check. And the same torrent removed and added again within half a second came back broken once. The import never removes, so the second only matters to the tests.

Not measured yet, and checked first in the build: reading those .torrent files through a container's bind mount, v2 and hybrid torrents on the two engines, a Deluge label's own "move completed" folder acting after an import's recheck.

3 · X1 and X2 · where it lives

The same two rows, on every engine

the server its .torrent files (X3)

X1The way inrecommended a

a: the file is the bridge. Each engine's group gets a Backup section with Export NAME's torrents and Import torrents into NAME. Moving a library is an export on one server and an import on the other, and the same file is also that engine's backup. Nothing new to learn, and C9's sheet, journal and result carry over. b: a move library… sheet that names two saved servers and runs both halves at once. One step instead of two, but it needs both servers saved and reachable at the same time, and it is a second way to do what the file does. c: only imports into the other engines, no export from them: half the work, but a library could then only leave qBittorrent, and most people asking come the other way.

X2Saying that this is how a library movesrecommended a

a: the section's scope line ends To move them to another server, export here and import there., on all three engines. b: nothing; the rows speak for themselves. c: a third row, Move to another server…, that exports and then switches to the other server's import sheet with the file picked.

Recommended: X1 a, X2 a. One file, three engines, six directions, and no second flow to keep right.

4 · X3 · the .torrent files of a Transmission or a Deluge

They are on the daemon's disk, so omaseed has to see that disk

A qBittorrent sends each .torrent over the API. The other two keep them in the daemon's own folder (Transmission's torrents/, Deluge's state/), which is not a download folder, so a path map made for downloads doesn't cover it. A daemon on this machine is the easy case: the file is readable where the daemon says it is.

X3When omaseed can't read themrecommended a

a: read them where they are; otherwise ask once for the folder; otherwise export links. The export row says which it is before it starts. With the files seen, the row is plain. Not seen (a container, another machine), the row offers their folder… to point at that folder as this machine sees it (a mount, a copy), remembered per server. With no folder given, each torrent goes into the file as its magnet link with its whole record, and the row says what that costs: the target has to fetch each one's details from peers before it can check the data, which a private torrent with no peers online never does. b: links only, always: simple, and the same everywhere, but every import then waits on peers and some never finish. c: no export unless the files are seen: honest, but a container user gets nothing.

Transmission's file follows tracker edits and Deluge's doesn't, so the record's trackers are always taken from the API, and the import adds what the .torrent lacks, as C9 already does.

Deluge takes only a-z 0-9 _ - in a label, so Field Recordings becomes field-recordings; the block shows each name that changes. A category's own folder isn't lost: every torrent keeps the folder it is in, and only the rule that files new ones there has no counterpart.

X4Categories, tags and labelsrecommended a

a: the table above: the category is the first label, both ways, so a library that goes to Transmission and comes back has its categories and tags again. The block lists the names as they will be and lets nothing be edited. b: the same, with each name editable in the block, as save paths are. More control, a longer sheet, and a renamed label is a thing the user can do afterwards in one step. c: into qBittorrent, labels all become tags and no category is made: nothing is guessed, but the rail's categories stay empty after a move.

X5What the target can't keeprecommended a

a: said before the import, counted, never a blocker. A can't be kept block with one line per thing and how many torrents it touches, and the same lines in the result. Things with no counterpart: a seeding-time limit (neither has one), an idle limit and all tags but one grouping (Deluge), what happens at the limit (Transmission stops only; Deluge stops or removes), automatic management and an incomplete folder per torrent (both). b: only in the result, after the fact. c: a line per torrent in a report file beside the import.

X6The check, on engines that differrecommended a

a: the same promise as C9, kept per engine. Everything is added stopped; renames and priorities are set before any check; Transmission's own check on add counts, and omaseed asks for one more after a rename; Deluge is asked for a recheck every time (its trust it's complete switch is never used); complete ones start if they were started, the rest stay stopped. C9's rule for a rename whose old and new names both exist is kept on all three, and matters more on Transmission, which would answer success and point at the wrong file. b: trust the source: skip the check for torrents that were complete, for speed. A check of a large library on slow disks takes hours, but a wrong folder then shows only when a peer gets bad data.

X7Torrents that come as linksrecommended a

These are X3's fallback and any torrent that never had its details. a: added stopped as links, counted apart: 12 as links: they check once their details arrive. When details arrive while omaseed runs, it sets that torrent's renames and priorities and asks for its check, from the journal; closed, the journal finishes them at the next start. b: added and left to the user. c: left out of the import, listed in the result.

Recommended: X4 a, X5 a, X6 a, X7 a. The sheet says what will change and what can't come, in counts, before anything is added; the import then behaves as C9's on every engine.

6 · X8 · the server the library came from

Two engines on the same files

After an import the torrents are on both servers. Seeding the same complete files from two engines is harmless. Downloading the same unfinished files from two engines is not: both write. C9 already leaves unfinished torrents stopped on the target, so nothing collides unless the user starts them there while the old server is still running them.

X8What omaseed does about the old serverrecommended a

a: it says, and touches nothing. The result's last line, when the file came from another server omaseed knows: They are still on OLD. Unfinished ones stay stopped here until you stop or remove them there. An import never changes the source. b: a tick in the sheet, stop them on OLD first, when OLD is a saved server: one step less, but an import that writes to two servers, and a half-finished run leaves both changed. c: a button in the result, remove them from OLD, keeping the files.

7 · X9 and X10 · order and words

What ships first

X9The orderrecommended a

Each step is a release (C33). a: into qBittorrent first: 1 Transmission exports, and a qBittorrent imports a file from another engine (X4, X5). 2 Transmission imports. 3 Deluge exports and imports. The first step is the move most people make, and it puts the hard part (X3) in front. b: out of qBittorrent first: Transmission and Deluge import, then they export. The easy half first, no .torrent problem, but it serves the rarer direction. c: all at once, one release.

X10The section's namerecommended a

a: Backup, as qBittorrent's, so a switch between groups lands on its like (K32). b: Torrents, since on these engines it holds nothing else. c: Backup and move.

8 · what it amends

The rulings it changes

  • C25 K33 a (qBittorrent only in v1) ends for torrents: Transmission and Deluge get the section and the two rows. It stands for settings: no settings export, import or copy on the other engines, and omaseed's own backup still keeps qBittorrent's settings only.
  • C14 E10 is this board. C9 gains a note per engine (where the .torrent comes from, the check, what isn't kept); its file, journal, save-path rows and result are unchanged.
  • The feature record: torrentsBackup turns on per engine as its step ships, and the Backup section follows it.
9 · building the recommended calls

Five pieces

  1. The record says its engine. The manifest names the engine that wrote the file (an older file is qBittorrent's). core/LibraryCrossing, pure data: X4's table both ways, Deluge's label spelling, and X5's list of what a target can't keep, counted over a file's records. tst_librarycrossing gets every row of §5.
  2. Transmission exports. engines/transmission/TorrentsExport: the record from torrent_get, renames found against the .torrent's own names, the .torrent read from the daemon's folder or the folder given (X3), else the link. Recorded fixtures; a live test on the playground and on the container one, which settles §2's open point.
  3. A qBittorrent reads a foreign file. TorrentsImport takes the crossing's categories and tags, and the sheet gets its two blocks. With this, step 1 of X9 ships.
  4. Transmission and Deluge import. One importer per engine behind the interface the sheet already drives: add stopped, then label, limits and queue place, renames, the check, the start (X6); links finished from the journal (X7). Deluge: priorities in the add, one torrent per call.
  5. Walks. backup-walk.sh grows a crossing: a library with a renamed folder, a skipped file, two tiers of trackers, a category and two tags goes qBittorrent → Transmission → Deluge → qBittorrent, checked on each server and on disk, and comes back with the same names, folders and bytes.
