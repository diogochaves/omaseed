The story's quiet edits

Since board 56 the details pane's what happened tells renames. It still misses the other things people do to a torrent without touching a byte of it: put it in another category, tag it, set its location in another client. One line does worse than miss them. Added reads into the category the torrent has now, so a torrent added into inbox and later put in music says it was added into music. This board rules which quiet edits are story lines and which stay settings, how each line reads on each engine (qBittorrent's categories and tags, Transmission's labels, Deluge's one label), edits made by omaseed and edits seen in a poll, moves the server makes by itself, several edits in a row, and where the record lives. It answers C38 R10.

1 · today, in an omabox

A category change rewrites how the torrent was added

  • What the story knows (core/TorrentStory, C24 H6 with C38): Added, each move omaseed made that the history keeps (C18 D8), Finished downloading, the failure and the error from the log, a move Deluge dropped, and each rename the record keeps. Its rule: only what omaseed knows for sure goes in.
  • Added's dim line is today's category: events() words it from torrent.category, the value now, not the one it was added with. On Deluge it reads with no label or into LABEL the same way; on Transmission it has no dim line (no categories, C14 E4).
  • Where a category or tag goes today. App::setCategory, addTags, removeTags; the outcome strip says NAME put in music, tagged live, untagged wip (Transmission: labelled, unlabelled; Deluge: labelled music, taken out of its label) for 6 s (C18). Then facts shows the value now, and nothing remembers what it was.
  • A location set elsewhere (qBittorrent's Web UI, another app): the move history notices only when it is asked about move back. The last-move block then reads moved again since: nothing to move back (C18 D7), and the story never says where the torrent went, or that omaseed didn't move it.
  • What a poll can see. Unlike file names, all of these are in every torrent's sync diff, on every engine's translation: category, tags, save_path, auto_tmm, the limits and the queue position. So each can be seen changing, whoever changed it. SyncEngine already does this for the name (C38 R4): never from the first full update, never for a torrent's first appearance.
  • Moves the server makes by itself. qBittorrent moves a torrent under automatic management to its category's folder when its category changes (or the category's folder does). Deluge's Label plugin gives a torrent its label's folder to finish into; omaseed reads that folder as the torrent's save path while it downloads (the engine matrix's inverse model), so the save path changes with the label and the files follow when it finishes.
  • Per engine (C14 E5, C25 K13–K15): qBittorrent one category (with a folder) and any number of tags; Transmission any number of labels, no category; Deluge one label (lower case, with a folder when set), no tags, none at all with the Label plugin off.

b: every edit is a line, limits and options too (Limits set · ↓ 2 MB/s, ratio 2.0). Complete, but the story fills with dials and the lines that matter scroll away. c: only the location; filing stays a setting. Then Added keeps telling a category it may never have had, and a tag added by another tool is never explained.

Recommended: Y1 a. The story is the torrent's life: where it is, what it's called, what it's filed under, what went wrong. A dial's history is noise; its value now is in facts.

4 · Y5 · the first line

Added tells the category it was added with

Y5Added's dim line once the category changedrecommended a

a: the category it came with: the oldest category (or label) line's was. A torrent put in music after it was added into inbox reads Added · into inbox, with Put in music above it. With no such line (never refiled while omaseed watched, or the line was dropped by Y10's cap) it reads the category now, as today: the best omaseed knows. b: Added drops the category whenever a category line exists, and the lines tell the rest. Honest, but the first line of a refiled torrent loses where it began. c: as today. The story then contradicts itself: Added into music under Put in music · was in inbox.

Tags and Transmission's labels are not in Added today and stay out: they are many, and the add sheet's tags are rarely the story. A category or tag given in the add sheet is no line of its own (C38 R8's rule: the story starts at Added).

5 · Y6 and Y7 · the location

Moves omaseed didn't make are moves too

Y6A location set outside omaseedrecommended a

The next poll shows a new save_path that no move of omaseed's made. a: the move line, with C18 D7's words: Moved to PATH · moved outside omaseed, at the poll that saw it. And the last-move block, which says why move back has nothing to do, names it:

The last-move block's sentenceWhen
moved again since: nothing to move backtoday, whoever moved it
moved since outside omaseed: nothing to move backa: when the story's newest place line is outside omaseed (Y6) or the server's (Y7)

b: the line, and the block as today. c: no line; only the block's sentence, which shows only while omaseed still keeps the move (C18 D8).

  • Not a move: omaseed's own move seen in a poll (a torrent in a running job, or in a record that landed in the last minute: the history's line already tells it); a torrent finishing out of its incomplete folder (its save path stays; Finished downloading tells it); a magnet's first path.
  • Nothing moved yet: a torrent still waiting in its incomplete folder only changes where it will go. Its line reads Will land in PATH instead of Moved to, with the same dim line. Landed is the rail's word for a finished download (C24 H2).
  • PATH is the save path, as an omaseed move's line shows it.

a: the same line, its dim line naming the cause when omaseed can tell it, whoever started it (omaseed's own category change, the category's folder changed in Settings, another client):

A category line and the move it causes, in the same poll, read the move above (the later act, as C38 puts a rename above a line at the same second). b: all of them moved outside omaseed. Simpler, and false when omaseed's own category change started it. c: no line for these. Then a category change moves gigabytes and the story only says Put in music.

Recommended: Y6 a, Y7 a. Wherever the data went, the story says where and, when it wasn't an omaseed move, why it went. The block's sentence stops guessing.

6 · Y8 · seen in a poll

Say when it wasn't omaseed, and when the name itself went

Y8Filing edits made outside omaseedrecommended a

a: the same lines, the dim line ending in changed outside omaseed (Tagged live gets it as its only dim line). Use the switch over §3's mocks to see it. Moves keep C18 D7's moved outside omaseed and renames C38's renamed outside omaseed: each says its own verb. b: a bare outside omaseed on every kind. Shorter, but alone it reads like a place. c: only omaseed's own filing edits. A script tagging torrents is exactly what goes unexplained.

  • A name removed from the server. A category, label or tag that leaves the server's list in the same poll that takes it off the torrent: the dim line says the category was removed, the label was removed or the tag was removed instead, whoever removed it. Every torrent that had it gets the line.
  • Its own echo: omaseed's own edit shows in the next poll too. A change that matches an edit omaseed sent for that torrent (pending, or answered within the last minute) is that edit, as C38 R4's rename echo.
  • While omaseed wasn't running: left out, as C38 R5. The first sync after start is never a line, nor a torrent's first appearance.
7 · Y9 · several in a row

A wrong tick fixed is no line

Y9Edits of the same thing, close togetherrecommended a

a: C38 R6's fold, per kind. Category (or label) edits of one torrent within 10 minutes, with no other line between, are one line: the last one's time, the first one's was. A run that ends where it began leaves no line. Tag edits fold into their net change: tagging live and untagging it a minute later leaves nothing, and tagging live then untagging wip reads Tags changed. Seen edits fold with each other, never with omaseed's. Places never fold: each move is its own line, as omaseed's moves are. b: each edit its own line, always. The action bar's tag list toggles one tag per click, so a few wrong clicks stay in the story. c: keep only each torrent's newest filing line, so older categories are lost even days apart.

8 · Y10 · the record

One record, a cap per kind

Y10Where the lines live, and for how longrecommended a

The server keeps none of this history, so it is omaseed's record, as renames are (C38 R9). a: the same record grows. core/RenameHistory becomes core/StoryRecord: its What gains category, tags and place, it is saved where it is now (beside the move history, per server; the C38 records read as before), kept while the torrent is in the library and dropped when it leaves. The cap is per kind: the last 10 names, 10 filing lines and 10 places per torrent, so a busy tagging week never pushes out a rename. b: one cap of 10 across them all. One number, but tags crowd out the rest. c: a second record beside the first. Two of everything (load, save, prune) for the same shape.

9 · out of scope

What this board doesn't draw

  • Limits, priorities, the queue, options, trackers, web seeds: settings (Y1), shown where they are today.
  • A torrent stopped by its share limit. That's the torrent doing something, not an edit, and the story doesn't tell it today. It could be an issue of its own.
  • A file renamed elsewhere: still unseen (C38 R3, R4).
  • Edits while omaseed wasn't running: left out (Y8, C38 R5).
  • The log view. omaseed's moves have a line there (C18 D7); whether filing and outside moves join it is not drawn here.
  • Notices and the outcome strip: unchanged. None of these edits sends a desktop notice.
  • The time column: board 56 noted that the app's 70 px column elides times that aren't today's; that fix is its own.
10 · what it amends

The rulings it changes

  • C24 H6 (with C38): what happened's events gain each filing and place line the record keeps, and Added's dim line comes from the oldest category line (Y5). Newest first (C32 D15) is unchanged; a place line at the same second as a filing line goes above it.
  • C38 R9: the record is the story's, capped per kind (Y10). C38 R10 is answered by this board.
  • C38 R2 and #201 F19 (the marks): a sixth kind, edit, in the accent with move and rename (Y4).
  • C18 D7: the last-move block's sentence names an outside or server move (Y6). Its rules for move back are unchanged. C18 D8 and the outcome strip are unchanged.
11 · building the recommended calls

Five pieces

  1. The record. core/RenameHistory renamed core/StoryRecord; What gains category, tags, place; By gains server; Y9's fold per kind (net tags, a run back to its start removed, places never folded); Y10's cap per kind; C38's JSON read as before. tst_storyrecord: each fold, the caps, the prune, the round trip, an old file.
  2. omaseed's own edits. setCategory, addTags, removeTags write a line per torrent on the server's OK (the category it had before, from the model), and note each send for Y8's echo, as noteSentRename does. Unit tests in tst_app's rename block's style.
  3. What a poll sees. SyncEngine reports a category, tags or save path that changed between two applied polls (never the first full update, never a first appearance), and the categories or tags that left the server in the same poll. App drops echoes (its own sends; a running move job's torrents and the last minute's records), and words the cause: Y7's category folder (qBittorrent's resolved folder for the category) or label folder, Y8's removed, Y6's incomplete folder (Will land in). tst_syncengine for the diffs.
  4. The story. The words of Y2, Y3, Y6, Y7 and Y8 in TorrentStory::events; Added's dim line (Y5); StoryEvent::Kind::Edit, kindName edit; DetailsStoryEvent.qml paints it as move; DetailsMoveBlock.qml's sentence (Y6). tst_torrentstory gets every row of §3's and §5's tables.
  5. Walks. actions-walk.sh already sets a category and tags: it goes on to read their lines, Added's fixed dim line, a fold, and a category and a tag set through the box's API (changed outside omaseed, the tag was removed); move-walk.sh sets a location through the API (moved outside omaseed and the block's sentence) and turns automatic management on under a category; transmission-walk.sh reads Labelled; deluge-walk.sh a label with a folder (Will land in · by its label).
