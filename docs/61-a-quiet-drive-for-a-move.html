A quiet drive for a move

A long move off a hard disk shares the disk's head with every torrent still seeding from it. Each piece a peer asks for pulls the head away from the move's long read. Stopping those torrents by hand before the move is the wrong fix today: the move starts again only what was running when it began (C20, #138), so the ones you stopped stay stopped, hundreds of them. This board proposes the move doing it: stop the drive's torrents for the move, and start exactly those again as each one lands or when the move ends. Not the ones you had stopped, not the ones you start meanwhile. It also says what nobody knows yet: how much time it saves. That gets measured before anything is built, and before any number goes on the sheet.

1 · today, in an omabox

A move leaves every other torrent alone

  • What the job touches. Only its own torrents: MoveJob sends them smallest first, three at a time with qBittorrent (M12). Every other torrent goes on seeding, and so do the job's own while they wait their turn.
  • What it remembers about running. Each of its torrents' wasRunning (not stopped, errored or missing its files) when first sent, saved in ~/.config/omaseed/moves/<server id>.json. The recheck after a move starts only those (C20). Nothing else about running or stopping is kept.
  • What omaseed knows about a drive. FreeSpaceProbe reads a folder's mount point, free space, filesystem and st_dev on this machine, through the path map, and only where it sees the server's disks. "The same drive" is one device (C15 M5, #240). Nothing reads whether a drive is a hard disk (/sys/block/…/queue/rotational) or how busy it is (/proc/diskstats).
  • The engines differ. qBittorrent and Deluge take a stop or a start at any time. Transmission answers nothing at all while a move's copy runs, set_location included (C25 K22), and moves one torrent at a time (#85).
  • What's known about the gain. #175 holds one big move off a hard disk without stopping anything: seeding kept getting its turn, and the move still read close to what that disk model is rated for. Its saving is an estimate from a spec sheet, not a run with and without. So there is no measured gain yet, and this board doesn't state one.
2 · P1 · measure first

The gain is an open item

Open: how much faster a move off a hard disk is with its torrents stopped.No number goes on the sheet, in a commit or in the docs until the runs below give one. The sheet's gain line (§4) waits for it, and P2's size floor is worked out from the rate the runs measure.

The playground can't answer this alone. A loop image on a fast drive has no head to move, so seeking costs it nothing. The kernel reports such a loop device as not rotating (queue/rotational 0). So the plan has two stages: one that proves the plumbing anywhere, and one that needs a real hard disk. That disk holds only a test library the script makes, never a real library.

StageWhereWhat runsWhat it answers
A · the plumbinga box's own qBittorrent (app-box.sh up -b … --qbt), a udisks loop image as stuck-walk.sh makes one, move-library.sh's library on it; the Transmission (:8085) and Deluge (:8086) playgrounds for their rowsthe move with and without the stop, a test switch reading the loop image as a hard disk; omaseed killed mid-move, a pause, an end, a torrent started by handthat exactly the set comes back, on every engine; no timing is read from it
B · the gainthe playground qBittorrent (:8081) moved, for the run, onto a profile whose library sits on a hard disk mounted for the test (USB or a spare internal one, by udisks). The leecher (swarm.sh leech start --rate KIB, :8084) is the seeding loadthe same move off the hard disk to a fast drive, alternating stopped and seeding, and moved back between runstime saved per load, and what the stop costs in upload
  • The library (B). Made by the script, never copied: about 40 torrents of random data, 0.5 to 4 GiB each, so the move runs long enough to read (tens of minutes). Plus 40 small torrents that aren't in the move, the "others". It all lives on the test disk, larger in total than the machine's free memory, so the page cache can't hold the move.
  • Cold every time. Before each run, every file of the library is evicted from the page cache with posix_fadvise(DONTNEED), which needs no root. qBittorrent is restarted so its own cache is empty too.
  • The load. Two levels, each its own set of runs: a light one (the leecher capped low) and a heavy one (uncapped), pulling from the moving torrents still waiting and from the others. Uploads are spread over many torrents, which is what scatters the reads.
  • What is timed. The move's own clock from the job file: first send to last landed. Beside it, sampled every 5 s from /proc/diskstats for the source disk: MB read per second, reads per second, and busy (io_ticks). For the destination: MB written per second. Plus the bytes the playground uploaded during the run, which is the cost.
  • How many. At least three pairs per load, run ABAB (stopped, seeding, stopped, seeding…) so the disk's warm-up and the time of day don't fall on one side. The result for each load is the median of each kind and the spread between runs of the same kind.
  • Transmission's own question (B, one pair). While Transmission copies, its daemon answers nothing (K22). Whether its other torrents still upload during the copy is unknown. The pair times a move on the Transmission playground with the leecher pointed at it. If they don't upload, there's nothing to stop there (P11).
  • The target (B, one pair, optional). The same with the seeding torrents on a hard disk you move to, for P12.

P1The bar the runs must clearrecommended a

a: build it only if stage B shows the stopped runs shorter by at least 10 % at the light load, and by more than the spread between runs of the same kind. The light load is the one most people have. If the saving is under 5 % at both loads, #175 closes with the numbers in its research folder and nothing is built. In between, the numbers come back to you for a call. b: build it now and measure afterwards, with the gain line waiting for the numbers. The stop-and-start-exactly-those part is useful even without a gain, since it replaces stopping by hand. But it costs the drive's seeding for a gain nobody has seen. c: drop it now. #175's run without the stop already read close to the disk's rated speed, which suggests seeding takes little.

3 · P2 to P4 · when, how and which

Offered on a hard disk, for a long move, off by default

P2Which moves get itrecommended a

a: a move across drives (a rename on one device gets nothing, C15 M5), off a drive omaseed sees and reads as a hard disk, with other running torrents on it, and big enough to be long. A hard disk is queue/rotational 1 on the disk under the folder's device, followed from a partition to its disk and through dm-crypt, LVM and md to the disks below. If any one below is a hard disk, the whole is one. Long is at least 10 minutes at the rate stage B measures off a hard disk, turned into a size floor once there is a rate. A selection's move and a folder's are both jobs (C16 L1), so both get it. b: any move across drives, SSDs too. Stopping torrents costs their seeding, and on an SSD the reads don't get in each other's way. c: hard disks, with no floor. Then a 2 GB move offers to stop 200 torrents for a minute.

A server whose disks omaseed can't see (C16 L13: a NAS, a container without a path map) never gets it: omaseed can't tell what the drive is, and won't guess. Some USB enclosures report an SSD as rotating, so P5 shows how busy the drive actually is, read on it.

P3Offered, on by default, or automaticrecommended a

a: offered in the Move sheet, off by default, and remembered per server for the next move (state.json, like the places list's recent destinations, C16 L4). Stopping torrents is something you decide to do, and the sheet is where the move is decided. b: offered and on by default. That's the right default only if the gain is large, so it would wait for P1's numbers. c: always, with a setting to turn it off. Hundreds of torrents stopping without anyone ticking anything is the kind of surprise a person notices days later on their ratio.

P4Which torrents it stopsrecommended a

a: every torrent running when the move starts with data on the source drive, the move's own included. Data on the drive means its save path, or its incomplete folder while it downloads, through the path map, on the source's device. The move's own torrents start again as each one lands, where they now read from the other drive. The rest start when the job ends. In a folder's move most of the drive's torrents are usually the move's own. Stopping only the others would leave most of the seeding running. b: only torrents outside the move, the issue's "other". It matches the words, and does little when the folder is most of the drive. c: only seeding ones, with downloads left running. A download writes to the drive and gets in the way as much. The sheet counts them (3 of them downloading) so you see what you'd hold up.

  • Left as they are: stopped, errored, missing files, and checking. Stopping a check throws its progress away, and a check is a long read the move can't hurry. Each is counted in the sheet's last dim line.
  • Running includes queued. A torrent qBittorrent has queued would start within minutes. Started again, it goes back into the queue (P10).
  • Fixed at the start. A torrent added during the move, or one that turns up on the drive meanwhile, isn't stopped. The set is what the sheet counted, checked again when the move starts.
  • The one moving now is stopped too: qBittorrent moves a stopped torrent the same (C20's stopped ones move in today's walk), and its own seeding reads are what the move least needs.

Recommended: P1 a, P2 a, P3 a, P4 a. The offer shows only where it can help: a long move off a hard disk omaseed can see. Nothing happens unless you tick it. It quiets the whole drive, the move's own torrents included, and gives each one back as soon as it's out of the way.

The verb is stop, never pause. Stop is what the app says for a torrent everywhere, and what qBittorrent 5 says. Pause and resume belong to the move itself (M11), and the paused band (§5) needs both words in one line. b: the tick alone, with no figures. Shorter, but you'd be deciding blind, and the issue asked for the drive's load. c: only the upload figure, read from the engine, which works without seeing the disk. But upload is not reads: a piece read once can be sent to many peers from the cache, so a busy drive can show a small upload.

5 · P6 and P7 · while it moves

One more part in the band, and you can always start one

the move

P6What you see during the moverecommended a

a: the band's second line ends with 174 stopped for the move, which counts down as the move's own land and start. The rows keep the status cell's stopped, since the column has no room for more (C20 found the same). Their tooltip and facts say stopped for the move to /mnt/fast/archive · starts again when it lands, or … when the move ends. The move's record in details lists the set, with show them (the table filtered to the set) and start them now, which lets the whole set go while the move keeps going. The palette has start what the move stopped. b: a band tool start them beside pause and show. One click closer, but the band's tools are the move's own, and a fourth crowds them on a narrow window. c: a new status word, held. It's clear in the table, but it's a state no engine has, and every filter, count and the bar widget would have to learn it.

P7You start one, or do anything else to it, meanwhilerecommended a

a: whatever you do to one of them wins. Start it from omaseed, the Web UI or any client, and the next poll sees it running: it's let go, never stopped again by this move, and not counted at the end. Stop it from omaseed (an explicit act on a torrent that already reads stopped) and it's let go too, and stays stopped after. Delete it and it's gone from the set. Move it off the drive yourself and it still starts at the end, since it was running before. b: the move stops again any it held that someone started. That's a fight with the person, and with any other client they use. c: ask each time. A question in the middle of a two-hour move, usually answered by nobody.

6 · P8 and P9 · pauses, quitting, crashes

Held only while the move is sending, and written down first

P8A pause, quitting, ending the moverecommended a

a: the set is held only while the job sends. Any pause starts them all again: yours, quit's pause and quit (M13), stuck (M14), no space, the first torrent failing, a refusal. The paused band says so: the 174 it stopped run again until you resume. Resume stops again those still in the set and still running, so P7's let-go ones stay let go. End the move starts them, as any end does. A quit that keeps the job running (keep running, hidden in the tray) changes nothing. Quit's line (J5) gains The 174 it stopped start again now. b: kept stopped through a pause and started only at the end. A move paused for the night, or stuck, would then keep a whole drive silent with nothing moving. c: as a, but pause and quit keeps them stopped until omaseed runs again. That holds the drive for as long as omaseed is closed, maybe days.

P9A crash, a logout, a rebootrecommended a

a: the set goes into the job file before the stop is sent, each torrent with how it was running (forced or not, queued or not). After a crash the job resumes at the next start (M13) and keeps holding them. The resumed band says 174 still stopped for the move. A torrent leaves the set in the file only once a poll shows it running, so a start that never reached the server is sent again. If the job can't go on (its server was removed from omaseed, or omaseed can't read the job's torrents), the set is started before the job is dropped. Removing a server that holds a set asks first, as removing one with a job does. b: also mark them on the server, with a tag on qBittorrent and a label on Transmission, so another client or a later omaseed can find them. Deluge has one label per torrent and it is the user's, so not there. It also writes into the user's own tag list and syncs to every client they use. c: nothing saved. A crash then leaves 212 torrents stopped and nobody knowing which.

What no design fixes: if omaseed never runs again, the set stays stopped. The file is plain JSON beside the job's, and a line in the README says what it is.

// in the job file, ~/.config/omaseed/moves/<server id>.json (proposed)
"held": { "drive": "/mnt/archive", "device": "8:17", "since": "2026-11-12T14:03:11Z",
          "torrents": [ { "hash": "…", "own": true,  "forced": false, "queued": false },
                        { "hash": "…", "own": false, "forced": true,  "queued": false } ],
          "let go": [ "…" ], "started": [ "…" ] }

Recommended: P5 a, P6 a, P7 a, P8 a, P9 a. The sheet says what it costs before you tick it. The band says how many are stopped for as long as they are. Anything you do to one wins over the move. A pause gives them all back, and a crash loses none of them.

7 · P10 · the end

Started as they ran, and said in the summary

P10What the end does and saysrecommended a

a: the summary's second line ends 212 started again, or with what happened to the rest: 209 started again · 2 you'd started yourself · 1 removed. A start the server refuses reads 1 didn't start, with the reason in details. Each starts as it ran: a force-started one is forced again, and a queued one goes back into the queue. A torrent of the move that failed isn't started, since its data may be half in each place. The summary's recheck (C20) starts it if it comes out complete, as it does today. The record keeps the set's counts for move back (C18 D7). A move back is a move like any other and gets the tick again. b: a separate outcome strip for the starts. The strip is for actions you just took (C18 D1), and this is the move's ending. c: say nothing; they're just running again. Then 1 didn't start has nowhere to go.

If that pair shows a cost, a short amendment to this board adds the target's torrents under the same tick. b: both drives' torrents whenever both are hard disks. Twice the silence, for a cost nobody has measured.

9 · not in this board

Out of scope

  • Slowing instead of stopping. The alternative speed limits (C4) or a per-torrent upload cap would keep peers connected. But every piece still costs the head a seek, and it changes a setting that belongs to you. If stage B has time, one pair with the alternative limits on answers whether it's worth a board.
  • Stopping a drive's torrents outside a move, as an action of its own (stop everything on /mnt/archive). The rail's folders and a selection already do it by hand, and starting exactly those again is only needed because a move ends on its own.
  • The busy-disk word (C17 D12, #123), saying a torrent is slow because its disk is busy. It may reuse DriveKind's reading, and stays its own issue.
  • Moves on SSDs and remote servers (P2), and the order of a move's torrents on the disk (M12 stays smallest first).
  • The bar widget (docs/20): unchanged, as C15 M20 left moves there.
  • A gain figure anywhere before P1's runs: not on the sheet, in a release note or in the README.
10 · what it amends

The rulings it changes

  • C15 M10 (the band): its second line gains N stopped for the move while a set is held. M11 (pause and end): both start the set again, and resume stops it again (P8). M13 (quit, restart): the job file holds the set, J5's quit line gains its sentence, and the resumed band says what's still stopped (P9). M16 (the end): the summary's line gains the starts (P10).
  • C16 L1: every job gets the tick where P2 allows it, a selection's and a move back's included. L3 (which checks show): the sheet gains one block, shown only when P2 holds.
  • C20 (#138): unchanged in effect. wasRunning is recorded before the stop, so the recheck still starts what you had running.
  • C25 K22 and the 2026-11-06 Transmission moves note: the stop goes before the first set_location, and starts only between moves.
  • C18 D1: unchanged. A quick move never reaches P2's floor, so the strip never tells starts.
11 · building the recommended calls

Six pieces, the measurement first

  1. Measure (P1). The research folder of §2, stage A's plumbing on the box and stage B's runs on a hard disk holding only the made library. Ends with the table and the call, built or closed, in its README and on #175. Nothing below starts until this one says go.
  2. The drive. core/DriveKind: hard disk or not, from /sys/dev/block/MAJ:MIN through partitions and slaves/ (dm-crypt, LVM, md); busy and read rate over a 5 s window from /proc/diskstats. A test switch (OMASEED_TEST_ROTATIONAL=MOUNT) reads a loop image as a hard disk in walks. tst_drivekind runs on a fake sysfs tree.
  3. The held set. MoveJob: P4's set counted at plan time and checked again at the start, written before the stop, let go by P7, started by P8 and P10, carried by P9, saved and restored. tst_movejob: a restart mid-job, a pause and a resume, an end, a cancel, one started by hand, one removed, a refused start, a failed one left stopped.
  4. The words. The sheet's block (P5) with its 5 s reading, the band's part, the paused, resumed and quit lines, the summary, the record's list with show them and start them now, the rows' tooltip and facts, the palette row. Both skins. tst_MoveSheet and the band's QML test.
  5. The engines (P11). Transmission's order around set_location and its gate, Deluge's auto-managed check, and qBittorrent's forced and queued put back. Engine tests, plus one step each in transmission-walk.sh and deluge-walk.sh.
  6. The walk. OMASEED_MOVE_WALK_FROM=quiet scripts/dev/move-walk.sh: a loop image read as a hard disk, the leecher on, the tick on. Then kill omaseed mid-move and start it again, start one by hand, pause and resume, end. Checked on the server: exactly the set started, the one started by hand untouched, a torrent stopped beforehand still stopped. Then a step in docs/manual-tests/moves.md.
