omaseed · board 62 · 2026-11-12 · a proposal · #163

An agent's way in

Ask your coding agent "why didn't my download finish?" and today it has nowhere to look. What omaseed knows (a torrent it couldn't write, a move that stopped on a full drive, the line qBittorrent logged about it) lives in the running app, and the agent shouldn't be poking at qBittorrent's files or API with your password. This board proposes the way in: four words, omaseed status, errors, log and moves, answered by the running omaseed over the D-Bus name it already owns, in the window's own words or as JSON. Then a fifth, omaseed do, for the fixes the window already offers. It stays off until you turn it on, and moving files always asks you first. It joins the words board 55 ruled for skins (C37): one family, one help page, one guide for agents.

1 · today, v0.9.2

Options that launch, a bus the bar widget uses, nothing to ask

  • What can already be read. The bar widget's status file, $XDG_RUNTIME_DIR/omaseed/status.json (schema v2, written at least every 10 s by a real launch, removed on quit), holds the server, counts, speeds, up to three downloads, recent completions, the servers as last seen and the shared menu. It holds no error text, no log line and no move.
  • What only the app knows. Why a torrent needs you: core/ProblemLog ties qBittorrent's log lines to torrents (C2), and core/RowWords turns them into the row's words and its fix (no access, qBittorrent can't write to …, fix move…). A move running now (core/MoveJob, its journal in moves/<server>.json) and the moves that landed (core/MoveHistory, C18, in state.json). qBittorrent's log itself is read only while the log face is open (core/ServerLog, C3 D9).
  • No gate today. Anything that runs as you can call Invoke("pause"), AddSources or Invoke("quit") on the bus with busctl. It can read your keyring too. A gate in omaseed can't be a lock against a program that means harm. It is a line that omaseed's own way in holds, and that the guide tells agents not to cross.
  • Board 55 is ruled and not built (C37, #221 to #227). Its words (check, skin clone|list|use) and --skill don't exist yet, so this board can share their dispatcher and help page before either is written.

3 · V3 to V7 · the way in

Who answers, in what shape, and when nobody can

V3How a word reaches the running omaseedrecommended a

  • aA new interface on the same name and object, io.github.diogochaves.omaseed.Agent, beside org.freedesktop.Application and Status: Status(s options) → s, Errors(s) → s, Log(s) → s, Moves(s) → s, later Do(s action, as torrents, s options) → s. Options and answers are JSON strings, so omaseed errors --json and busctl --user call … Errors s '{}' print the same bytes, and the shape lives in one place (core), not in D-Bus types. The widget's Status interface and its contract stay as they are.
  • bThe same methods on Status. One interface fewer, but the widget's contract (plugin/STATUS.md) would then carry the agents' too, and change whenever they do.
  • cNo bus at all: the status file grows errors, the log and moves, and the words read it. The file is rewritten every second while anything moves, the log costs a request to qBittorrent each time it's read, and a file can't be asked the lines after 4120.

A word runs on a QCoreApplication: no display, so it works over SSH as long as the session bus is reachable (it is, under systemd, for the same user). Without a session bus, today's local socket stays the hand-off's and --quit's only. The words say omaseed isn't reachable, and don't grow a second protocol.

V4The answer's shape, and how it stays stablerecommended a

  • aOne "v": 1 for the whole family, check and skin list included, in an envelope every word shares: v, command, at, omaseed (its version), then the word's own fields. The status file's rules: fields are added within a v, and changing or removing one is a new v; numbers are numbers, bytes are integers, lists are always present. Times are ISO 8601 in UTC ("2026-11-12T14:03:11Z"), because the reader is a model and a person reading over its shoulder. Ids are never translated ("cause": "noAccess"), and next to them sit the window's own words ("fact": "no access"). With --json, stdout is always one JSON object, a failure too: {"v": 1, "command": "errors", "error": {"code": "not-running", "message": "…"}}.
  • bA version per word (errors v1, check v3). Each can change alone, and the guide has to keep a table of which is which.
  • cNo version, as C37 U5's example has. Fine until the first change breaks somebody's script without a word.

This adds v, command, at and omaseed to the JSON of #224 (check) and #223 (skin list). C37 U5's version stays the skin's own version, as it is there.

V5When omaseed isn't runningrecommended a

  • aSay so and exit 3. omaseed isn't running, so it can't answer. Open it (or start it in the tray with omaseed --hidden) and ask again. No word starts it, and none reads omaseed's files instead: state.json and moves/ aren't a contract, and the guide says never to touch them (C37 U4). A running omaseed older than the word (an update installed while it ran) has no Agent interface: The omaseed that's running is 0.9.2, older than this one (0.10.0). Quit it and open it again to answer. Exit 3 too.
  • bStart it hidden and answer. A question would then sign in to your server, start the seed ledger and maybe send notices, and leave omaseed running when nobody asked for it.
  • cAnswer what's on disk (the move history, the servers as last seen), marked "live": false. Two readers of the same files, one of them with no lock and an old idea of their format.

V6More than one serverrecommended a

  • aThe server omaseed is on, unless --server NAME (a name or an id) says another. status lists every server, the current one live and the others as last seen (C12, the status file's servers). errors and log can only come from the server omaseed is on, because it watches no other: for another one they say omaseed is on attic, not seedbox. errors reads only the server omaseed is on. and exit 4. moves answers for any server, from that server's saved history and journal. No word switches servers.
  • b--server switches omaseed to that server to answer. A question that changes what the person's window shows, with no word to them.
  • cEvery server, every time: omaseed would sign in to each to answer, which it never does today (C12), for a question.

V7What a read may showrecommended a

  • aReads are open while omaseed runs, with no setting. They carry torrent names, folders and log lines: that is what an agent needs to say why something failed, and the status file already gives the names to anything running as you. They never carry a credential, an API key, a cookie or an address with a password in it. The guide tells the agent that what it reads goes to its model's provider, and to ask before it reads a whole library to answer a question about one torrent. That's the same concern that made C37 U6 refuse a window shot. Here the agent reads one answer to one question, never everything on screen.
  • bReads behind a switch too, off until asked. An agent's first omaseed status then fails, and the person goes to Settings to allow what the status file already gives away.
  • cNames hidden unless --names. Most answers become a torrent failed, and the agent runs it again with the flag anyway.

Recommended: V3 a, V4 a, V5 a, V6 a, V7 a. A new interface beside the widget's, JSON from end to end, one version for the whole family. A word answers only while omaseed runs, and only about the server it is on. Reading needs no permission. Acting is another matter (§5).

4 · V8 to V13 · the four reads

The window's words, in a terminal

The examples are invented: a qBittorrent called attic, a Transmission called seedbox, fictional torrents and folders. Long hashes are cut short here; the JSON carries them whole.

V8status: what it saysrecommended a

  • aThe head of the window, in a few lines: the server and its engine, whether it answers (and C12's words when it doesn't), speeds and the alternative limits' pick, the rail's five questions counted (C24 H2: needs you, arriving, landed today, giving back, resting), moves running, a pause held (C36 M10), and the other servers as last seen. When something needs you, the last line points at errors.
  • bThe status file's whole content as it is (v2). One schema fewer, but it's the widget's: top seeders, a week of uploads, today's .torrent files in Downloads, the menu rows. Most of it is noise to an agent, and it would tie the widget's format to the agents'.

V9errors: what it listsrecommended a

  • aThe rail's "needs you", each with the window's words: errored torrents, the yellow failures (C2 D1: a move, a rename or a part file that didn't happen), a stuck move (docs/44 D13), missing files. Each one gets its row's fact and sentence (RowWords), when it started, its fix as the window offers it and, once actions exist, the omaseed do that runs it. On qBittorrent it also gets the log lines tied to it, at most 3. The server's own problem, if any, comes first. Before answering, omaseed reads the log once (qBittorrent), so a failure that happened while the window was hidden is in it (C2 reads every 15 s only while it shows). Failures dismissed in the window are counted, not listed.
  • bTorrents in an error state only. Simpler, and it misses what C2 exists for: the move qBittorrent answered OK and then didn't make.

V10log: how much, and on which enginesrecommended a

  • aqBittorrent only, warnings and worse, the last 50 lines, read from log/main at once, one request through omaseed's own session. --level normal|info|warning|critical (that level and worse), --lines N (up to 2 000), --since ID (the lines after it: the JSON's next is the id to pass next time) and --torrent HASH (C3 D13's rule for which lines are about a torrent). Oldest first, as the face (C3 D12). Over the first line it says where qBittorrent's memory of its log begins (C3 D15). On Transmission or Deluge: seedbox runs Transmission, which keeps no log omaseed can read. omaseed errors has each torrent's own error text. Exit 4.
  • bEvery level by default, as the face opens. A busy qBittorrent's info lines (each add, each tracker answer) bury the two warnings the agent came for.
  • cNo log word: errors already carries each torrent's lines. That leaves the lines that are about no torrent out of reach: a port that didn't open, a full disk before any torrent noticed.

V11moves: running and landedrecommended a

  • aThe move running now, if any, and the last 5 that landed (--landed N, up to what C18 D8 keeps). A running one gets its title, where it's going, its state in the band's words (moving, paused and why, stuck, carrying the loose files) and its counts. A landed one gets its torrents with their folders before and after, and what a move back would do now (C18 D7: go back, moved again since, moved outside omaseed, gone).
  • bRunning moves only. That answers is it done? and not where did my folder go yesterday?, which the history is there for.

V12Without --jsonrecommended a

  • aShort lines in the window's words, as above: the server first, one block per torrent or move, times in the story's words (14:03, yesterday 21:10). Colour only on a terminal: ANSI's red, yellow, green, blue and bright, which Omarchy's terminals paint in the theme's own colours. None when the output is piped or NO_COLOR is set. Failures go to stderr, answers to stdout. Lines wrap at the terminal's width, else 80.
  • bThe JSON, pretty-printed, always. One output to keep right, and a person who runs omaseed errors has to read braces.
  • cA table per word. Neat for moves, and too narrow for a sentence like qBittorrent can't write to …, which is the point of errors.

V13Exit codesrecommended a

  • aOne table for the family, C37's 0, 1 and 2 kept: 0 answered or done · 1 the skin doesn't read (C37) · 2 usage · 3 omaseed isn't running, can't be reached, or is too old to answer · 4 that server can't answer this now (not the current one, unreachable for log, an engine with no log, an unknown torrent) · 5 not done: not allowed, refused, or nobody answered (actions) · 6 asked, and the server refused it (actions). An answer that finds errors is still 0: the agent reads the count, and a script run under set -e doesn't die on good news about bad torrents.
  • b0, 1, 2 only, the reason in the JSON. Shorter to learn, and a shell script can't tell not running from refused without parsing.

5 · V14 to V18 · acting, later

The fixes the window offers, if you say so

The second step of #163. An agent that has read no access, fix: move… would like to run that fix. These calls settle which fixes, how an agent asks for one, and how you allow it. They're built after the reads ship (V20).

V14Which actions, and which always askrecommended a

  • aThree tiers. Fixes, which change nothing on disk and can be undone: retry, start-here (C25 K24), recheck, reannounce, pause and resume (C36 M10's hold, the whole server), dismiss (a failure, as x on its block). Moves, which move your files and fill drives: move --to FOLDER (a job, with every check a move from the window gets: room, names already there, C15) and move-back MOVE (C18). They always ask you, whatever the setting. Never through do: delete (with or without files), rename, categories and tags (a category can move files under automatic management), adds, settings, servers, credentials, quit. Those stay yours, in the window.
  • bFixes only, never a move. Safer, and the most common fix (move… for a folder qBittorrent can't write) stays out of reach.
  • cEverything the window does, delete included, each behind the ask. One allow clicked without reading deletes a library.

V15The commandrecommended a

  • aomaseed do <action> <torrent…> [--to FOLDER]: one word, the actions named as above (the fix.do that errors gives). A torrent is named by its hash or a unique prefix of at least 8 characters, never by its name, which can be shared or retyped wrong. omaseed do --list says what the setting allows now. The word waits for the outcome (and for your answer, when it asks) and says what happened in the outcome strip's words (C18 D1).
  • bA word per action (omaseed recheck, omaseed retry…). Ten more names that could clash with a file, and nothing tells reading words from acting ones.
  • comaseed fix <torrent>: runs whatever fix the window shows for it. The shortest call, and the agent can't say what it's about to do until it's done.

V16The gate: one row in Settingsrecommended a

  • aSettings › General › Agents: read only · ask me · let them fix. Read only is the default, and the package and the first run never change it. Ask me asks for every action. Let them fix runs the fixes at once, and moves still ask. The gate is held in the app (Do on the bus), not in the word, so busctl meets the same gate. While the row isn't read only, a second line says what happened last.
  • bOff and on only. Then on has to mean either ask every time (tiring after the tenth recheck) or never ask (moves included).
  • cA switch per action. Exact, and nine switches for a feature most people turn on once.
agents

V17The askrecommended a

  • aA small window where you are, as the add window opens (C35 W1, W3: floating, centred on your workspace, its size fixed, titled omaseed · agent for a Hyprland rule). It says what and on which torrents, for a move where to, how much and the room there, and which program started the word: the parent process of the omaseed do that asked, read from /proc. omaseed can't tell who is behind a command, and says so. No key allows it: you were probably typing in the terminal when it took focus, so ↵ does nothing until a button has the cursor (tab). esc, closing it or 2 minutes without an answer refuse.
  • bA desktop notice with allow and refuse. It never takes focus, but a notice's buttons are easy to click by accident, and some notification daemons hide them behind a menu.
  • cA sheet in the main window. It brings omaseed's workspace up, the jump C35 removed for adds.
asks to

V18Saying it was an agentrecommended a

  • aWhere the act shows anyway, with two words more. The outcome strip, if the window shows: Recheck started · Lantern Festival Field Recordings · by an agent (C18 D1). The story, for moves (C24 H6): Moved to /data/music, its dim line by an agent, as C38 R4 says renamed outside omaseed. omaseed's own log (the journal): agent: recheck on 1 torrent, allowed in the window (claude, pid 48213). And the Agents row's last line (V16).
  • bAs a, plus a list of the last 20 things agents did, in Settings. A history to keep, for a feature built to do small things.
  • cNothing extra. A recheck nobody remembers asking for then reads as qBittorrent's own.

Recommended: V14 a to V18 a. The window's own fixes and nothing that deletes. One word, do, with torrents named by hash. One row, read only until you say otherwise, and moves always ask, in a window that a stray ↵ can't answer. Whatever an agent did says so where you'd look.

6 · V19 and V20 · the guide, and the order

One guide for agents, and reads before actions

V19The guiderecommended a

  • aU4's guide, in two parts: your library (the words, their JSON fields, the exit codes; never qBittorrent's API or files, never the widget's Status interface; that answers go to the model's provider (V7); do and its tiers once they ship) and skins (C37 U4's). Both are in the AGENTS.md written to ~/.config/omaseed/, and omaseed --skill prints all of it. It stays short: the reference is in the JSON and in omaseed help <word>. An agent asked about a download is rarely started in ~/.config/omaseed/, so the help page's last line is what sends it to --skill.
  • bTopics, omaseed --skill library and --skill skins. Shorter prints, and an agent has to know a topic exists to ask for it.
  • cA second file, LIBRARY.md, beside AGENTS.md. The skill splits, which C37 said it shouldn't.

V20The orderrecommended a

  • aReads first, released on their own; actions after, from this same ruling. Under omaseed's version rule (one board is one feature: its first step takes the minor number, later steps patch numbers), the reads are the minor release, and the gate and do follow as patch releases. The shared words come first, whichever of this board and board 55 is built first. Nothing waits for skins.
  • bRule the reads now and give the actions a board of their own once the reads are in use. Slower, and the gate is designed today with what the reads teach still unknown.
7 · not on this board

Left out, on purpose

  • A shot of the window. C37 U6 stands: no word captures the open window. check draws invented torrents, and the reads answer in text.
  • Following, and signals. No --follow, no --watch, no D-Bus signals: an agent asks again (log --since makes that cheap). The bus stays methods only.
  • Controlling a running move (go on after a nearly full drive, pause, end it): the band's buttons, in the window. A later board could add them as moves-tier actions.
  • Delete, rename, categories, tags, adds, settings, servers, credentials, quit through do (V14). --quit already exists for the person's scripts, and the widget's AddSources stays the widget's.
  • Search, the seed console, the seed ledger. A seed word could read the console's figures later. Nobody has asked an agent about them yet.
  • Transmission's and Deluge's logs. omaseed can't read one. errors carries their own error text.
  • A protocol server for agents (an MCP server or the like). The words are the interface. A wrapper is a few lines for whoever wants one, and not omaseed's to ship.
  • Another person's omaseed, over the network. Only the session bus of the user who runs omaseed.
  • Knowing which agent asked. The ask names the program that started omaseed do, as a fact, not as proof of who it is.
