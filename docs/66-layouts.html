omaseed · board 66 · 2026-11-20 · a proposal · #288

Layouts

Board 55 let the person's agent change how omaseed looks. This board lets it change how omaseed is arranged: which blocks a view shows and in what order, the table's columns, where the details sit, where the speeds go. Only the blocks omaseed already has. A layout is data, read all or nothing at the file like a skin, and checked without a display. Nothing here is built until it is ruled.

Already ruled (2026-11-20, #288, option c). A layout is its own file beside the skin, as herdr keeps its themes and layouts apart. The Settings rows that are layout choices edit that same file: one truth, nothing to arbitrate, no "a row you touched wins" and no "set by the skin". Look and arrangement mix freely: Console's look with the person's own block order is one skin and one layout. Data only, no code, no new blocks. This board builds on that; options a and b of #288 are not redrawn.

1 · the inventory

Every arrangement omaseed has today, and what it becomes

Each choice is one of three things. Layout: where a block is, whether it shows, how wide. Look: how a thing is drawn; it stays a skin token or a setting. Behaviour: what omaseed does, or which words it uses; it stays a setting. Clicks of the moment (a fold, a sort, a scope's own display) stay in state.json, as herdr keeps its clicks apart from its layout files.

The headline. Of the fifteen rows in Settings › Appearance, three are layout (Add window, Details panel, Speeds), plus one row in General (Show the Servers group in the rail). Most of a layout has no row today: the table's columns (saved per server), the library's display, the rail's groups, the rows display's five groups, the details tabs and the seed console's eleven blocks. Those are fixed in QML or kept per server, and become keys of the file.

2 · LY1 and LY2 · the file

One folder per layout, beside skins/

LY1 alayouts/<name>/layout.json, shaped like a skinrecommended

Under $XDG_CONFIG_HOME/omaseed/, the same folder rule, name rule and version rule as a skin (C37 U1): the name is the folder, version is 1, a newer version is not drawn. The folder leaves room for RECIPE.md and preview.png when a layout is shared, as U9 does for skins. Every list of blocks has the same two keys, order and hidden; a block the file doesn't name keeps its default place and its default visibility, so a block a later omaseed adds still shows up.

{
  "$schema": "../../layout.schema.json",
  "version": 1,
  "cloned_from": { "layout": "default", "version": 1 },
  "description": "Table first, details below, speeds in the status line.",
  "library":  { "display": "table" },
  "rows":     { "order": ["needsYou", "arriving", "landed", "givingBack", "resting"], "hidden": ["resting"] },
  "table":    { "order": ["name", "progress", "status", "dlspeed", "upspeed", "ratio", "category"],
                "hidden": ["size", "seedsPeers", "swarm", "eta"],
                "widths": { "status": 140 } },
  "rail":     { "order": ["now", "folders", "categories", "trackers", "tags", "servers"], "hidden": ["tags"],
                "width": null },
  "details":  { "placement": "bottom", "order": ["story", "files", "trackers", "swarm", "webSeeds"],
                "hidden": [], "width": null, "height": 260 },
  "console":  { "columns": [["attention", "totals", "tide", "year"],
                            ["keepingAlive", "ratioLadder", "trackers", "earning"],
                            ["holding", "onAir", "lately"]] },
  "speeds":   "status",
  "addWindow": "one"
}
  • Every key is optional. A missing key is the default layout's value; an empty file with only version is the default layout.
  • Widths are base-12 units, as columnWidths are today, so a base-size change scales them; null or a missing width is the default (or, for the rail, the skin's density.railWidth).
  • The schema, layout.schema.json, is generated from the reader's table and written beside skin.schema.json on every start, under the same header rule (C37 U4).

LY1 blayouts/<name>.json, one file each, as herdr does

Shorter to type. No room for a recipe or a preview beside it, and a different shape from skins/ for the agent to learn.

LY2 aOne built-in, default: today's arrangementrecommended

The default layout is written out once in C++ (as SkinReader::omarchyTokens() is for Omarchy's skin), shipped and never written to disk. It is today's omaseed exactly, so a person who never touches a layout sees nothing move. It is called default, not omarchy: an arrangement belongs to no look, and default under Console's skin reads right. default joins the reserved names (with omarchy, console, desktop).

Console gets no layout of its own. Board 46's station (numbered plates, a specials column) was an arrangement with blocks omaseed doesn't have, and C46 ruled it out. Console today is a look over the default arrangement, and stays that.

LY2 bdefault, plus a shipped console layout

A second built-in so Console's look comes with an arrangement of its own (the table first, the rail wider, details below). It couples a look to an arrangement again, which option c just pulled apart, and the station itself would need new blocks.

LY2 cNo built-in; the default is whatever the code does when no layout is chosen

Nothing to clone from by name, so layout clone has no source and an agent starts from an empty file and the schema.

3 · LY4 · what a layout may say

Arrangements omaseed already draws, and nothing else

LY4 aToday's arrangements only, with two guardsrecommended

A layout may order and hide the blocks of every list in §1 (the rail's groups, the rows display's groups, the table's columns, the details tabs, the console's blocks), set the widths a drag sets today, and pick among the placements omaseed already has: the details auto, right or bottom; the speeds in the title bar or the status line; the add window in one or two columns; the library's display.

It may not add a block, run code, name a file, or say a colour, a size of type or a gap: those are a skin's. Placements omaseed can't draw today (the rail on the right, the status line on top, a fourth console column) are not keys; each would be a board and a build of its own, and then a key.

  • Needs you stays shown and first in the rows display, and attention in the console. A torrent that needs the person must never be arranged out of sight. A file that hides or moves them has that dropped, with why.
  • Name stays shown in the table, as the columns palette already holds it.
  • Hiding a block hides it from that view only. Its keys, its commands in the everything palette and the agent's words still work. The details tabs' digits follow the shown tabs; a hidden tab still opens from the palette.

LY4 bAlso new placements: the rail on the right, the status line on top

Closer to "where the rail sits" in #288's words. Each needs a build (mirrored rail, focus order, the split's grip) before a key can say it, and makes this board's build twice the size.

4 · LY3 and LY5 · Settings edits the file

Appearance, split in three

Per option c, the rows that are layout choices write into the layout in force; nothing in state.json holds them any more. Appearance becomes three groups: Look (the skin and what draws), Arrangement (the Layout row, then the rows that edit it) and In the desktop (the bar, the widget, the Omarchy menu). Settings › General loses Show the Servers group, which moves to Arrangement.

LY3 aA row edits the layout in force; on default, the first edit makes minerecommended

The built-in is never written. When the person is on default and changes a layout row, drags a column or a split, or ticks a column, omaseed clones default into layouts/mine/ (mine-2 if taken), writes the change there, switches to it, and says so once under the Layout row: Saved as your layout mine. On a layout of the person's, the row writes into its file straight away.

  • omaseed writes only the key that changed, keeping every other key, description, $schema and the key order; a drag writes once, on release, as today.
  • The folder is watched (debounced, compared by content, as skins are): the agent's save redraws, and a row shows the file's value at once.
  • A file that doesn't parse, or is a newer version, is never written: the green rows are off and the yellow line says to fix the file first (as not-written, C37). Drops don't block a write.

LY3 bRows locked on a built-in

On default the green rows are greyed with "clone to change". Honest, and a dead end for someone who only wanted the details at the bottom.

LY3 cEdit the built-in in place, move it aside later

herdr's way: a shipped file edited anyway is moved to <name>-edited on the next start. omaseed's built-in isn't a file, so there is nothing to move; this would mean shipping it as one.

LY5 aSettings edits what it edits today; the rest is file onlyrecommended

The four rows, the columns palette, the grips and the split are the layout's controls in the window. The new lists (rail, rows, details tabs, console) have no control yet: the person's agent edits them, and the Arrangement group ends on one row that says so, with open file. A control for them can follow if people ask.

LY5 bA new Arrangement pane with a drag list per view

Every list reorderable and hideable by hand. A large piece of UI for a feature whose first users arrive through their agent.

5 · LY6 and LY7 · one layout, or one per place

One layout for the window; a scope keeps its own display as a click

LY6 aThe layout says the library's display; a scope's own pick stays in state.jsonrecommended

C24 H4 already splits this: the library's display is what every scope without its own shows, and picking one inside a folder or a category sets that scope only. The first is an arrangement, so it becomes library.display; the display menu in the library writes it into the layout. The second is the person's memory of a place, so it stays in displays.scopes. OMASEED_DISPLAY still pins every scope for a run and writes nothing.

LY6 bDisplays stay out of layouts entirely

The display menu keeps writing state.json only. Simpler, and a layout that says "table first" can't.

LY6 cThe layout holds every scope's display too

Folder paths and category names in a file meant to be shared, and a layout that means nothing on another library.

LY7 aOne table arrangement for every serverrecommended

Today the columns and widths are saved per server (tables.<server>), mostly by accident of where the table's state lives. A layout is the person's, not a server's: one table for all. A column an engine has nothing for shows as it does today on that engine. Sort and folds stay per server in state.json.

LY7 bA layout may say columns per engine

"table": { "qbittorrent": {…}, "transmission": {…} }. Closer to today for someone with two engines, and a heavier file for everyone else.

6 · LY8 · skins and layouts

They mix; neither names the other

LY8 aKept apart: a skin can't name a layout, a layout can't name a skinrecommended

As option c says. Settings has two rows and the CLI two words, and any skin goes with any layout. The one place they touch is the rail's width: a skin's density.railWidth stays its proportion (Console's rail is wider), and a layout's rail.width, when set, wins over it, as a drag wins today. Every other density token stays the skin's.

LY8 bA skin may suggest a layout

"layout": "station" in skin.json, applied when the skin is picked. Brings back the arbitration option c removed: which wins when the person's layout says otherwise.

7 · LY9 and LY10 · bad files and the check

Read like a skin, checked like a skin

LY9 aDrops with why; a file that can't be read draws default, the choice keptrecommended

C37's rules, word for word where they fit. A key the reader can't use is a drop {key, value, why} and the rest is drawn: an unknown block (not a column omaseed knows), a block named twice (named twice; the first kept), a guard (needs you is always shown), a width out of range (32 to 1200 units, as the grips). A file that doesn't parse, or has a newer version, is drawn as default with the reason in the Layout row's yellow line; the choice is kept, and the next good save draws it. A chosen folder that is gone does the same and never stops a start.

LY9 bAny drop draws default

Stricter, and a typo in one column name throws away the whole arrangement.

LY10 aomaseed check --layout NAME [SKIN]: the verdict and one picture of the windowrecommended

A sibling of C37 U5, with its rules: no window, no D-Bus, no server; the demo library; the person's theme, base size and fonts. It prints the reader's verdict and dropped, and draws one picture of the whole window as the layout arranges it (rail, the library's display, details open on a demo torrent, the speeds where they go) under the skin in force, or SKIN when given. --display rows|table|space|console draws that display instead. One picture, not a light and a dark: a layout has no colour. Exits as check: 0 drawn, 1 drawn whole as default, 2 usage. The file is ~/.cache/omaseed/check/<layout>.layout.png.

$ omaseed check --layout mine
mine: drawn, 1 dropped
  rows.hidden "needsYou": needs you is always shown
picture: ~/.cache/omaseed/check/mine.layout.png (table, Omarchy's skin, tokyo-night)

LY10 bThe verdict only

Enough to catch a typo, not enough for an agent to see that the details landed at the bottom.

8 · LY11 · the words, the guide, the skill

omaseed layout list|clone|use

LY11 aThe skin's three words, for layoutsrecommended

omaseed layout list [--json], omaseed layout clone <from> <name> (every key written out, cloned_from recorded, an existing name refused) and omaseed layout use <name> (the running instance over the Agent interface, UseLayout, else the saved choice appearance.layout, every other key kept). Codes as C37: unknown-layout, bad-name, layout-exists exit 2, unreadable 1, not-written 5. OMASEED_LAYOUT=NAME picks one for a run, as OMASEED_SKIN; the walks and ctest pin default, so the person's layout never reaches a test.

LY11 bOnly layout use; the agent copies files by hand

Fewer words, and no cloned_from, so nobody can tell later what a layout started from.

  • The guide. AGENTS.md gains a layouts part beside the skins' (the folder, the keys, the guards, check --layout, clone before you change), and layout.schema.json is written beside skin.schema.json.
  • The skill. Board 65 (#286), drawn alongside this one, shapes the skill; whatever it rules, the skill gains a layouts page.
  • Sharing. A shared layout is a folder with layout.json, RECIPE.md and preview.png (from check --layout), topic omaseed-layout, as U9.
9 · LY12 · the first start

What state.json holds today becomes the person's layout

LY12 aA layout called mine only when something differs from the defaultrecommended

  1. On the first start of the version that reads layouts, omaseed gathers the arrangement in state.json: the three Appearance rows, the Servers group, the rail's width, the library's display, and the table of the server in use (its columns, order, widths, details sizes).
  2. If all of it is the default, nothing is written and the person is on default.
  3. Otherwise omaseed writes layouts/mine/layout.json with only the keys that differ, cloned_from the default, the description Your arrangement before layouts., and chooses it. A folder mine already there is never touched: mine-2.
  4. The old keys are read no more, left in state.json for one release so going back a version loses nothing, then removed with the dead three (§1).

Other servers' column arrangements are not carried (LY7 a): one table for all.

LY12 bAlways write mine

Everyone gets a file, even with nothing in it but the defaults, and every later default change has to reach it by hand.

LY12 cStart everyone on default

Simplest, and the person's columns and details placement are lost on the update.

11 · building the recommended options

Five pieces

  1. The reader. LayoutReader beside SkinReader: the default written out in C++, the table of keys and their checks, drops with why, the guards, the folder list and watch. QtTest for every drop.
  2. The window reads it. The rail, the rows display, the table, the details tabs and the console take their order and visibility from it; the three placements and the widths too. A test that the default layout draws today's window.
  3. Settings writes it. The Layout row, the three groups, the green rows and the palette, grips and split writing one key; clone on the first edit; the migration.
  4. The words and the check. layout list|clone|use, UseLayout, OMASEED_LAYOUT, check --layout, the guide's part and the schema.
  5. The proof. scripts/dev/layouts-walk.sh: in a box, a row edit makes mine, an agent-style save redraws, a bad key and a broken file, layout use live and quit, check's picture; DECISIONS, the changelog.
